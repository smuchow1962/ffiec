## Headline

The chain spec ships an unusually mature supply-chain story for a regulatory-banking specification. `docs/supply-chain.md` already names cosign + GPG dual signing, hermetic and reproducible builds, SLSA Level 3 provenance per SLSA v1.0, CycloneDX SBOM publication, signed-binary attestation in §10.7, the conformance corpus as a versioned signed artifact, the cold-DR key with annual dry-run attestation consumption, and explicit revocation procedures including a documented dual-compromise window. Most regulatory specs in 2026 ship with one of these primitives; this spec ships nine. **My read pass found twelve places where the supply-chain story is named but not fully composed across SLSA, Sigstore, in-toto, SBOM, and SSDF — and where the AI/ML model-supply-chain dimension that the chain naturally captures is not yet developed.**

The twelve questions cluster into four groups: (a) SLSA / Sigstore / in-toto composition gaps where one framework is named without its complement (SLSA L3 without Rekor transparency-log inclusion; cosign without in-toto Layout for the multi-step build pipeline), (b) SBOM / SSDF / OSV alignment with federal-procurement and OpenSSF Scorecard requirements, (c) reproducible-build extension to the verifier-binary-as-evidence-tool case where the examiner's own supply-chain integrity is at stake, and (d) AI/ML model-supply-chain attestation where the chain captures `gen_ai.request.model` and `gen_ai.response.model` but not provenance of the model artifacts themselves.

None of the gaps undermine the chain's integrity claim. All affect the spec's eligibility for adjacent supply-chain scoring frameworks (OpenSSF Scorecard, GitHub artifact attestations, OMB M-22-18 SSDF self-attestation), the trustworthiness of the verifier binary in adversary-against-the-project scenarios, and composability with downstream consumers' supply-chain integrity tooling. Each question carries a concrete close-out path that layers onto `docs/supply-chain.md` without disturbing the spec's normative core.

## Supporting questions

### SQ-1. SLSA Build Level alignment across SDK, ledger, and verifier — single attestation or three?

**Question.** `docs/supply-chain.md` claims SLSA Level 3 for "the build pipeline" producing the verifier binary, with the per-release `verifier.intoto.jsonl` attestation. The chain ecosystem has three load-bearing software components: the SDK (links into the institution's application and produces chain entries), the ledger server (ingests entries, produces seal records), and the verifier binary (produces the PASS/FAIL evidence the examiner relies on). The doc's SLSA L3 claim names the verifier explicitly and the ledger server in passing; the SDK's SLSA Build Level is not stated. Per SLSA v1.0 §"Build Track," each artifact carries its own provenance attestation. An SDK shipped under SLSA L1 (developer-laptop build) while the verifier ships under SLSA L3 creates an asymmetric trust path the regulator's supply-chain examiner will catch — and the SDK is the component running inside the institution's application processes producing the chain entries.

**Status:** Partial.

**Closing language proposal.** Add to `docs/supply-chain.md` an explicit per-component SLSA Build Level table: SDK (each language SDK ships under SLSA Level 3 minimum; per-release `sdk.intoto.jsonl` attestation), ledger server (SLSA Level 3 minimum; per-release `ledger.intoto.jsonl`), verifier (SLSA Level 3 minimum; existing `verifier.intoto.jsonl`). For each component, name the build platform identity, the source-control authentication, and the provenance signing identity. The deployment-gating control extends from "validate `verifier.intoto.jsonl`" to "validate every per-component `*.intoto.jsonl` attestation for the components the institution deploys." The institution's CC8.1 control description names the SLSA-verifier procedure for each component.

### SQ-2. Sigstore Rekor transparency-log inclusion — cosign signing without Rekor is authentication only, not transparency

**Question.** The supply-chain doc names cosign + Sigstore as the primary trust path. Cosign uses Sigstore's Fulcio for short-lived certificate issuance and Sigstore's Rekor for transparency-log inclusion. Cosign signing without Rekor inclusion provides authentication (the signature verifies against the project's pinned cosign public key) but not transparency (an external observer cannot independently confirm that a signature was issued). For supply-chain scenarios where a vendor-side compromise could include silent re-signing under the legitimate cosign key (a SolarWinds-class scenario), Rekor's transparency log is the canonical detection mechanism — every legitimate signature appears in the public Rekor log; an unexpected signature absent from Rekor is anomalous. The supply-chain doc says "Sigstore is the trust root" but does not require Rekor inclusion or specify how the institution validates Rekor membership at deployment-gating time.

**Status:** Partial.

**Closing language proposal.** Add to `docs/supply-chain.md` §"Cosign signing" a normative subsection: "Every cosign signature produced by the project's release pipeline MUST be appended to the Sigstore Rekor transparency log at signing time. The institution's deployment-gating control validates Rekor inclusion alongside cosign signature validation: the validator (cosign verify --rekor-url ... or equivalent) confirms the signature's Rekor log entry is present, the entry's signing identity matches the project's release-management identity (Fulcio short-lived certificate's GitHub OIDC claim or equivalent), and the entry's inclusion proof verifies against Rekor's signed tree head. A signature that validates against the project's pinned cosign key but is absent from Rekor is non-conformant and triggers IR Scenario 3 (signature verification failed) with branch (d) `Rekor inclusion missing`." This composes the existing Sigstore claim with Rekor's transparency property and gives the supply-chain examiner an independently observable signal.

### SQ-3. in-toto Layout Manifest for the build pipeline — pipeline-shaped attestation, not just artifact-shaped

**Question.** SLSA L3 attestation provides one provenance statement per output artifact: "this binary was produced by this build platform from this source." The in-toto Layout Manifest 2024 spec attests every STEP in a multi-step pipeline (source checkout, dependency fetch, compile, test, sign, release-publish) with per-step attestation binding the declared functionary, inputs, and outputs. SLSA names provenance availability; in-toto Layout names step-shape-conforming-pipeline. The two compose: SLSA gives you "this binary came from this platform"; in-toto gives you "this platform's pipeline followed the declared steps with the declared functionary identities." Without the Layout, an attacker who compromises the release-management role's pipeline definition (alters which steps run or which functionary signs) can produce an SLSA L3 provenance attestation that is technically valid but pipeline-divergent. The supply-chain doc names build-pipeline properties (hermetic, reproducible, audited) but does not publish an in-toto Layout Manifest binding the pipeline structure as an attestation.

**Status:** Partial.

**Closing language proposal.** Add to `docs/supply-chain.md` §"Build pipeline" a subsection "in-toto Layout Manifest (informative for v1.0; normative for v1.1)": the project publishes an in-toto Layout Manifest per the in-toto Layout Specification 2024 declaring the build-pipeline steps (source-checkout, dependency-fetch, compile, test, sign, release-publish), each step's expected functionary identity (Fulcio short-lived cert, GPG fingerprint, or hardware-token serial), each step's expected input and output material, and the chain of step attestations binding step N's outputs to step N+1's inputs. The Layout Manifest is signed under the project's cosign key with Rekor inclusion. Institutions that operate in-toto-aware tooling (e.g., the Tekton chains controller, the GitHub artifact-attestations validator) may opt into pipeline-shape validation in addition to per-artifact provenance validation, providing defense-in-depth against pipeline-structure subversion. v1.0 ships the Layout Manifest informatively; v1.1 makes pipeline-shape validation a deployment-gating control alongside SLSA-verifier.

### SQ-4. SBOM format selection — CycloneDX 1.6 vs SPDX 3.0 vs both

**Question.** `docs/supply-chain.md` names CycloneDX 1.5 SBOM publication. CycloneDX 1.6 (late 2024) adds critical fields 1.5 lacks: explicit support for ML model components via `component.type=machine-learning-model` (composes with the chain's `gen_ai.request.model` capture), formula-based composition for derived components, signed SBOMs per JSON Schema Forms, and OpenSSF Vulnerability Disclosure Report integration. SPDX 3.0 (2024) similarly adds AI/ML profile coverage through SPDX-AI 3.0 and improved transitive-dependency modeling. NTIA SBOM minimum elements accept either format, but federal procurement under OMB M-22-18 tracks toward both formats in parallel for downstream-consumer flexibility, and CISA's SBOM-a-rama 2024 findings recommend dual-format publication for federal-agency vendors. The doc's CycloneDX 1.5 commitment is below current best practice and does not anticipate the AI/ML composition story.

**Status:** Partial.

**Closing language proposal.** Update `docs/supply-chain.md` §"What ships per release" to specify CycloneDX 1.6 (not 1.5) and add SPDX 3.0 as a co-published parallel SBOM. Add a subsection "AI/ML model-component SBOM" naming that the SBOM uses CycloneDX 1.6's `component.type=machine-learning-model` for any model component the SDK / ledger / verifier ships with (e.g., a tokenizer model, a classification model used in the verifier's anomaly-detection path, or model-fingerprinting weights), plus SPDX-AI 3.0 profile coverage in the parallel SPDX SBOM. Update §"SBOM consumption" to note that institutions feeding SBOMs to vulnerability management (Snyk, Mend, JFrog Xray) consume the format their tooling supports; the dual-format commitment removes the institution's tooling-choice gating dependency on the project. The dual-format commitment also positions the spec for federal-agency procurement under OMB M-22-18 where the SSDF self-attestation requirement composes with SBOM availability.

### SQ-5. NIST SP 800-218 SSDF mapping — federal procurement requires SSDF self-attestation

**Question.** OMB Memorandum M-22-18 (September 2022) and follow-up M-23-16 (June 2023) require federal agencies' software providers to self-attest compliance with NIST SP 800-218 SSDF v1.1. CISA's Secure Software Development Attestation Form (June 2023) is the canonical document. National banks regulated by OCC, federal-chartered credit unions regulated by NCUA, and federal-agency-adjacent banking infrastructure (FedNow participants, FRB-supervised entities) are inheriting SSDF self-attestation as a supplier requirement. The supply-chain doc names SLSA L3, FIPS 140-2 L3, hermetic builds, and audit logging — these compose with SSDF's PO / PS / PW / RV practice families — but does not publish an SSDF practice-by-practice mapping, which is what CISA's attestation form expects.

**Status:** Partial.

**Closing language proposal.** Add a new section to `docs/supply-chain.md` titled "NIST SP 800-218 SSDF mapping (informative)" with a table mapping each SSDF v1.1 practice to the supply-chain control that satisfies it: PO.5.2 (Secure Environments) → hermetic build environment; PS.1.1 (Protect Code from Unauthorized Access) → multi-maintainer review and signed commits; PS.2.1 (Verify Software Release Integrity) → cosign + GPG dual-signing; PW.4.1 (Reuse Well-Secured Software) → published CycloneDX SBOM + vulnerability scan; RV.1.1 (Identify Vulnerabilities) → published scan reports + the §4.3.2 emergency-patch SLA. The mapping makes the project's SSDF self-attestation form a derivative document published alongside each release. Institutions submitting downstream SSDF attestation to federal agencies cite the project's published mapping.

### SQ-6. Reproducible builds for the verifier binary — examiner-side rebuild as the trust-floor

**Question.** `docs/supply-chain.md` names byte-for-byte reproducible builds with the Go toolchain flags. This is excellent for the institution that rebuilds independently. But the verifier-as-evidence-tool case has a stronger requirement: the FFIEC examiner using the verifier as forensic evidence in a matter where the institution and the consumer (CFPB-disputing customer, plaintiff class) may have adverse interests needs the binary's provenance to flow back to source independent of the project's signing key. The Reproducible Builds project's standard goes beyond byte-identical output: it expects a published `buildinfo` file recording every build input (toolchain version, dependency versions, build flags, environment variables, source-tree hash) and a published rebuild attestation from at least one independent rebuilder. The supply-chain doc mentions reproducible builds but does not commit to publishing a `buildinfo` file or to operating independent-rebuilder attestation.

**Status:** Partial.

**Closing language proposal.** Update `docs/supply-chain.md` §"Reproducibility" to: (1) commit to publishing a per-release `buildinfo` file in the Reproducible Builds project's standard format, listing every input the build consumed (Go toolchain version, dependency module versions, build flags, source-tree commit hash, hermetic-environment image hash); (2) operate an independent-rebuilder attestation pipeline where at least one non-project-controlled rebuilder (a separate cloud account, a partner foundation, a CMU-SEI test rebuilder, or an FFIEC working-group-coordinated rebuilder) rebuilds from source on each release and publishes a signed rebuild-attestation; (3) publish the rebuild-attestations on the project's release page alongside `verifier.intoto.jsonl`. The institution's reproducible-build evidence (the existing `reproducible-build-log` JSON) becomes one input among at least three (project-built binary, project's SLSA L3 attestation, independent-rebuilder attestation), each independently validatable. This raises the trust-floor for the verifier-as-evidence-tool case from "trust the project's published binary" to "trust the binary if at least three independent parties rebuild from source and produce identical bytes."

### SQ-7. AI/ML model-supply-chain attestation — chain captures model_id but not model provenance

**Question.** The chain captures `gen_ai.request.model` and `gen_ai.response.model` (spec §4.4) for every chain entry representing a model call — the model identifier requested and the model identifier the vendor's API responded with. The chain does NOT capture the model's supply-chain provenance — training-data manifest, training-code commit, model-weights hash, model-card URL, model-fingerprint, or any cryptographic attestation by the provider that the model was produced by the declared training pipeline. Hugging Face's model-attestation work (Sigstore-signed model artifacts since late 2024), the OpenSSF Model Signing project (early 2025), and the proposed in-toto AI Layout extension all address this gap on the model-producer side. The chain naturally composes with model-provenance attestation: when a provider ships a model with cryptographic provenance, the chain entry could capture the attestation alongside the model identifier so the institution's downstream evidence claim becomes "we recorded calling model X (chain integrity), model X was the declared production model from provider P (chain attribute), and provider P attests model X was produced by training pipeline T (model-supply-chain attestation)."

**Status:** Partial.

**Closing language proposal.** Add to spec §4.4 a new optional attribute `gen_ai.model_provenance` (string or bytes) capturing the provider's model-supply-chain attestation when one is shipped. Schema: a JCS-canonical JSON envelope containing the model identifier, the producer identity (provider's signing key fingerprint or model-hub URL), the training-pipeline identifier (commit hash of training code, training-data manifest hash, hyperparameter set hash), and the provenance signature. The chain captures the attestation byte-for-byte under the OTel envelope per §5; the verifier ignores the attribute for chain-integrity decisions (parallel to the existing `gen_ai.provider_attestation` posture in §4.4). Add an informative section to `docs/supply-chain.md` titled "AI/ML model-supply-chain composition" describing the three-layer evidence model: chain integrity (the chain proves recording integrity); model identity (the chain attribute names the model); model provenance (the captured attestation, validated separately, proves the named model was produced by the declared training pipeline). This positions the chain for emerging AI-supply-chain frameworks (NIST AI RMF Generative AI Profile, EU AI Act Article 12 logging requirement composing with Article 13 transparency requirement on model provenance, the OpenSSF Model Signing v1 work) without requiring spec changes that depend on those frameworks finalizing.

### SQ-8. Ledger storage subservice supply-chain composition — S3 / Azure Blob / GCS as supply-chain inputs

**Question.** The ledger storage layer for many deployments rides on managed cloud storage (AWS S3, Azure Blob Storage, Google Cloud Storage). These services have their own supply-chain attestation: the cloud provider's SLSA / SOC 2 / FedRAMP / ISO 27001 reports cover the storage subservice. The chain spec's supply-chain story is silent on how the institution composes the chain's own supply-chain attestation with the storage subservice's supply-chain attestation. For the deployment-gating control to be meaningful end-to-end, the institution needs to know: when the ledger writes a chain entry to S3 with object-lock retention, does the institution have any evidence that S3's underlying implementation was produced by AWS's documented pipeline (i.e., is the S3 service itself supply-chain-attested at a level the institution accepts)? AWS publishes SOC 2 + FedRAMP for S3 but does not publish per-service SLSA attestation. The institution's defense-in-depth posture under §10.5 (HSM custody) and §10.13 (evidentiary artifacts) implicitly inherits the cloud provider's posture; the supply-chain doc should make this composition explicit so the institution's CC8.1 control description names the inheritance and the SOC engagement tests it.

**Status:** Nit.

**Closing language proposal.** Add a short subsection to `docs/supply-chain.md` titled "Subservice supply-chain composition (informative)" naming that the ledger storage subservice (S3, Azure Blob, GCS) carries its own supply-chain attestation independent of the chain project's, that the institution's CC8.1 control description names which storage subservice is in use and which supply-chain attestation (the cloud provider's SOC 2 / FedRAMP / ISO 27001 / SLSA where available) the institution consumes annually for the subservice, and that the SOC-pack subservice-organization scoping (carve-out method per Marcus's MQ-6 in drop #10) names the subservice's supply-chain posture as a complementary user-entity control. This composes Aaron's lens with Marcus's existing recommendation without duplicating it.

### SQ-9. Chain artifacts as SBOM/attestation inputs to downstream consumers — verifier-output attestation

**Question.** When an examiner uses chain artifacts as evidence in an FFIEC examination, a CFPB matter, or class-action litigation, the chain artifacts (the chain file, the seal record, the verifier output) become inputs to the consumer's own integrity-verification chain. The verifier produces a PASS/FAIL output that travels to the consumer (EIC working papers, plaintiff expert deposition exhibits, regulator enforcement file). The supply-chain doc covers the verifier binary's provenance — institution validates SLSA L3 + cosign + reproducible-build before deploying — but does not cover the verifier's output as a downstream supply-chain artifact. Reuven (drop #04 Q-16) raised the cryptographic dimension: the verifier output is not signed; institutions rely on capture-and-archival for evidence completeness. The supply-chain dimension is parallel and complementary: the verifier's output should ship with its own supply-chain context — which verifier binary produced it (binary SHA-256), which release version, which provenance attestation handle — so the consumer reading the output can validate the producing-verifier's supply-chain posture independently of the institution's discretionary archival.

**Status:** Partial.

**Closing language proposal.** Add to spec §7 (or to design/07-verifier-design.md) a normative subsection "Verifier output supply-chain manifest": the verifier emits a `verifier-output-manifest.json` alongside every PASS/FAIL run capturing the verifier binary's SHA-256, the verifier's release identifier, a content-addressed reference to the verifier's `verifier.intoto.jsonl` SLSA attestation (via Rekor URL or cosign signature handle), the chain file's SHA-256, the seal record's SHA-256, the run timestamp, and the PASS/FAIL disposition with reason string. The manifest is plain JSON (no signing required at v1.0; cryptographic signing is a v1.1 candidate per Reuven's Q-16). The downstream consumer reading the manifest can independently re-fetch the verifier's SLSA attestation, validate the verifier binary's supply-chain posture, and confirm the manifest's binary SHA-256 matches the attestation's output hash. This closes the verifier-output-as-supply-chain-input gap without expanding the chain's normative cryptographic surface, and composes naturally with Reuven's Q-16 cryptographic-signing extension if it lands in v1.1.

### SQ-10. Cross-vendor verifier conformance attestation through in-toto step attestation

**Question.** Spec §10.12 (verifier CLI exit-code contract) means multiple vendors can ship verifiers that conform to the same exit-code semantics. The vendor-conformance attestation procedure (`docs/vendor-conformance-attestation.md`, referenced from `docs/supply-chain.md` §"Vendor-conformance attestation") covers the case where a vendor attests their implementation passes the FFIEC conformance corpus. The procedure today is informal — vendor signs an attestation document; institution validates the signature; institution archives. An in-toto step attestation gives this procedure a structured shape: every "vendor-X verifier passes corpus version Y" attestation is an in-toto step attestation with declared functionary identity (vendor's signing key), declared materials (corpus version Y's SHA-256), and declared products (vendor verifier binary's SHA-256 + the test-execution log's SHA-256). The institution's validation is no longer "trust the vendor's PDF" but "validate the in-toto step attestation per the in-toto Specification 2024." This composes with the existing vendor-conformance registry (per `docs/supply-chain.md` §"Vendor-conformance attestation") and gives the registry a structured machine-readable backing format.

**Status:** Partial.

**Closing language proposal.** Update `docs/vendor-conformance-attestation.md` to specify the attestation format as an in-toto step attestation per the in-toto Specification 2024, with a published JSON Schema. Required materials: corpus version (named) + corpus tarball SHA-256 (matching `test-vectors-v{version}.tar.gz` published by the project); required products: vendor verifier binary SHA-256 + test-execution log SHA-256 + PASS/FAIL summary. The attestation is signed under the vendor's cosign key with Rekor inclusion (per SQ-2). The institution's validation procedure becomes mechanical: validate the in-toto step attestation signature, confirm Rekor inclusion, confirm corpus version match, confirm the test-execution log's PASS summary, archive all four artifacts. The project-side working-group-operated registry (per `GOVERNANCE.md` §"Vendor-conformance attestation registry") publishes attestations as in-toto step attestations rather than free-form PDFs. This raises the conformance-attestation rigor across vendors and makes the registry mechanically queryable.

### SQ-11. Conformance corpus integrity attestation through Sigstore + in-toto

**Question.** The conformance corpus at `spec/test-vectors/` is a load-bearing artifact: every vendor's implementation is conformance-tested against it, and corpus subversion that produces wrong-but-deterministic output across implementations is the textbook supply-chain attack against the chain ecosystem. `docs/supply-chain.md` already addresses this thoughtfully — the corpus ships as a versioned signed tarball with cosign + GPG signatures, the spec content-hash manifest covers per-test-vector files, and the institution's defense is to rebuild the corpus from the spec text and confirm against `spec-manifest.sha256.asc`. What's missing is the in-toto step-attestation framing: the corpus is the product of a multi-step process (spec authoring → test-vector generation → working-group review → working-group approval → release publication), and each step has a functionary identity. Today the corpus signature attests "this tarball was signed by the project's cosign key"; an in-toto Layout for the corpus would attest "this tarball is the output of the declared spec-authoring → test-generation → working-group-approval pipeline, with each step's functionary identity captured."

**Status:** Partial.

**Closing language proposal.** Add to `docs/supply-chain.md` §"Spec text and conformance corpus integrity" an in-toto Layout subsection: the spec working group publishes an in-toto Layout Manifest for the conformance corpus declaring the corpus-production pipeline steps (spec authoring with the spec-text commit hash, test-vector generation from the spec text with the generator binary's SHA-256, working-group review with the reviewer functionaries' signatures, working-group approval with the WG-chair signature, release publication with the release-manager signature). The Layout Manifest is signed under the project's cosign key with Rekor inclusion. The institution's corpus-integrity validation extends from "validate the cosign signature on the tarball" to "validate the in-toto Layout Manifest's pipeline-shape conformance," providing defense-in-depth against a corpus subversion that compromises the release-publication step but leaves the upstream working-group-review step intact (a SolarWinds-class scenario where the attacker compromises the build pipeline but cannot retroactively forge the working-group-approval functionary signatures). This is the highest-leverage in-toto application in the spec because the corpus is the conformance-bar floor across the ecosystem.

### SQ-12. CVE / vulnerability response posture and OSV.dev alignment — published SLA composes with §4.3.2 algorithm-rotation SLA

**Question.** Spec §4.3.2 commits to a 30-day spec-patch publication SLA on credible cryptographic-attack demonstration. The supply-chain doc names "Trivy + Grype scan results published per release" and an emergency-patch process triggered by post-release vulnerability discovery. What's not yet published is the project's vulnerability-response posture composing with industry-standard advisory channels: the OSV.dev vulnerability database, GitHub Security Advisories (GHSA), the CVE Numbering Authority assignment, the OpenSSF Vulnerability Disclosure Working Group's coordinated disclosure recommendations. For an institution operating SBOM consumption per `docs/supply-chain.md` §"SBOM consumption," the institution's vulnerability-management tooling (Snyk, Mend, JFrog Xray) ingests OSV.dev / GHSA feeds and matches against the SBOM. A chain SDK CVE that ships only as a project-side announcement without OSV.dev / GHSA publication is invisible to the institution's standard vulnerability-management pipeline. The 30-day SLA on cryptographic-attack patches needs to compose with OSV.dev / GHSA publication windows (typically 7 days from credible report) so the institution's tooling sees the vulnerability through standard channels.

**Status:** Partial.

## Stopping criterion

This drop carries 11 Partial + 1 Nit findings against the v1.0 spec and the supplementary `docs/supply-chain.md`, all clustered around supply-chain attestation composition. None affect the spec's cryptographic-integrity claim or the implementation contract. All affect the chain's eligibility for OpenSSF Scorecard scoring, federal-procurement bidder readiness under OMB M-22-18, downstream-consumer supply-chain integrity composition, and natural composition with the AI/ML model-supply-chain dimension that adjacent frameworks (NIST AI RMF Generative AI Profile, EU AI Act Article 12-13, OpenSSF Model Signing) are crystallizing in 2026.

The chain spec's supply-chain posture is unusually mature for a regulatory specification — most banking specs in 2026 ship with one or two of the primitives this spec ships with nine. The twelve questions are gaps in cross-framework composition and in extending the existing story to all components and to the AI/ML model dimension; they are not gaps in substance. Closing them takes the chain from "industry-leading among regulatory specs" to "reference example for OpenSSF / SLSA / in-toto / Sigstore / SSDF / OSV downstream consumers" without disturbing the spec's normative core.
