## Headline

The FFIEC chain-of-custody v1.0 spec is **cryptographically sound and operationally defensible for US banks operating under FFIEC oversight**. **For Israeli banks operating under Bank of Israel Directive 361 and the Israeli National Cyber Directorate (INCD) threat model, the spec has three load-bearing gaps that require institutional compensating controls or spec amendments before deployment is responsible.**

The gaps are not cryptographic. The three gaps are: (1) **Supply-chain compromise scenario is underspecified.** The spec assumes the vendor (Herald.Compliance) and the HSM are trustworthy; the INCD threat model assumes they are compromised within 18 months. The spec does not name controls sufficient to detect or recover from vendor compromise of the OTLP collector, the SDK, or the HSM firmware. (2) **Persistence-detection latency.** The daily Merkle seal gives a 24-hour detection window for HSM-side tampering. Against a nation-state APT with 18 months inside, detecting at 24 hours is excellent — but the spec does not clarify whether hourly seals are conformant, and does not address recovery-time asymmetry (detection in 1 hour vs recovery in 24 hours). (3) **PPL Amendment 13 cross-border transfer rules are not addressed.** Israeli banks cannot legally flow AI-decision data (including chain tokens) to non-Israeli cloud without explicit INCD approval and PPL-compliant transfer mechanisms. The spec allows vendor-hosted topologies (US or EU cloud); Israeli deployment requires institutional choice to self-host or to negotiate INCD-compliant cross-border terms with the vendor.

Tal does NOT file a Partial on these gaps. The gaps are manageable through institutional compensating controls documented in Directive 361 §5 incident-response procedures and in the institution's INCD coordination procedures. But the spec could serve Israeli banks better by naming the nation-state threat model explicitly, by clarifying supply-chain defense points, and by directing Israeli users to the PPL Amendment 13 compliance framework.

**Tachles (bottom line).** A Tier-1 Israeli bank deploying this chain would: (1) self-host or negotiate INCD-compliant vendor terms (rule out commodity US cloud), (2) implement vendor-compromise detection via build reproducibility and verifier supply-chain discipline, (3) run hourly seals instead of daily seals (if the HSM vendor supports it), (4) integrate with the INCD red-team program to test the chain's resilience under simulated APT scenarios. With these compensating controls, the chain significantly strengthens the bank's cyber-resilience posture under Directive 361. Without them, the chain becomes a liability: it creates a single point of integrity (the HSM signature) and a high-value evidence target for an APT (stealing the chain compromises decision audit trails). The difference between "strengthens resilience" and "becomes a liability" is institutional discipline, not spec changes. But the spec should make this choice explicit for Israeli readers.

## Supporting questions

### Q-1. Supply-chain compromise detection — can Tal rebuild the SDK and verifier from source and get byte-identical binaries?

The INCD threat model assumes a capable nation-state adversary can compromise software supply chains (CDN, npm, GitHub Actions, build caches, SBOM poisoning). The spec does NOT address verifier supply-chain compromise detection beyond cosign signatures and reproducible builds. Tal would ask: can he download Herald.Py SDK source, download the Go verifier source, run `bash build.sh --release` (or equivalent on Windows), and confirm the resulting binary's SHA-256 matches the published binary's SHA-256? If yes, supply-chain compromise is detectable. If no (or if the build requires secret keys, or involves external dependencies that auto-update), the verifier binary is a black box and an APT could have substituted a version that silently passes forged chains. **Ask:** Add to supply-chain.md or design/07-verifier-supply-chain.md: "Reproducible verifier builds: (1) The verifier source code is published at [GitHub URL]. (2) The verifier is built reproducibly using [Nix / Bazel / tinygo with pinned stdlib versions]. (3) A Tal-like adversary downloads the source, builds locally, compares SHA-256 against the published binary. SHA-256 match confirms the binary is unmodified. (4) The build is pinned to specific versions of stdlib, crypto libraries (no auto-updates). (5) Any divergence in published binary SHA-256 is reportable as a supply-chain compromise event. (6) The reference implementation (Go) documents the exact build command and the expected SHA-256 output. Conforming verifier implementations in other languages MUST state whether reproducible builds are supported and MUST document the pinned dependencies."

### Q-2. OTLP collector in-flight tampering — does the spec assume TLS 1.3 is unbreakable?

The OTLP wire carries chain-of-custody events between SDK and ledger. The spec (§5.1) mandates TLS 1.3 for encryption in transit. But the INCD threat model includes a nation-state actor who can potentially: (a) intercept OTLP packets (network-position adversary), (b) perform a TLS downgrade attack (force TLS 1.2 if the endpoint accepts it), (c) compromise the CA that signed the TLS certificate, or (d) compromise the SDK's certificate-pinning list. The spec acknowledges residual risk (section 2.1 of threat-model.md), but does not name institutional controls for OTLP-level assurance beyond "encrypt in transit." For an Israeli bank processing USD correspondent payments, OTLP tampering could affect cross-border transfer decisions. **Ask:** Add to design/05-otlp-wire.md or design/07-transport-security.md: "OTLP transport-layer security against network-position adversaries: (1) TLS 1.3 minimum; TLS 1.2 is deprecated and MUST be disabled on the production endpoint by [date]. Clients that negotiate TLS 1.2 are rejected with a clear error message ('TLS 1.2 not supported; update client'). (2) Certificate pinning (RECOMMENDED for tier-1 banks): the institution publishes the ledger server's certificate public key, and the SDK pins to it at build time. A man-in-the-middle with a valid-but-different certificate is rejected. (3) Mutual TLS (mTLS): the SDK certificate is issued per institution, and the ledger verifies the SDK certificate before accepting the OTLP stream. This prevents an attacker who compromises the CA from issuing arbitrary client certificates. (4) HPKP (HTTP Public Key Pinning) headers on OTLP/HTTP endpoints: the endpoint publishes a backup public key in the HPKP header, allowing fallback certificate validation if the primary key is compromised. (5) Institutional monitoring: the institution's network team monitors TLS handshake anomalies (cipher-suite downgrades, certificate-chain mismatches, connection-reset patterns that suggest a MITM). Anomalies trigger investigation."

### Q-3. HSM firmware compromise — is the Ed25519 signature really under the bank's control?

The spec §4.3 claims the HSM holds the Ed25519 signing key and the signature is cryptographically integrity-bearing. But the INCD threat model includes HSM firmware compromise (a nation-state actor modifies HSM firmware to sign arbitrary payloads on demand, or to leak the key after N uses). The spec accepts HSM physical-compromise risk as residual (threat-model.md R3, DFA / fault-injection attacks) but does NOT address firmware compromise risk. The spec assumes FIPS 140-2 L3 validation proves firmware integrity; this assumption is weak against a nation-state actor. **Ask:** Add to design/04-hsm-custody.md or threat-model.md section R3.1: "HSM firmware-compromise scenario and residual risk: (1) **Threat:** A nation-state actor with access to HSM vendor supply chains (firmware development, shipping pre-load, or in-field update channels) modifies the HSM firmware to sign arbitrary roots without verification, or to leak the signing key after N uses. (2) **Detection:** Institutions SHOULD implement firmware-attestation checks if the HSM vendor provides them (e.g., AWS CloudHSM attestation, Azure HSM attestation). The SDK or ledger periodically queries the HSM for a cryptographic attestation of the firmware version and compares against the known-good firmware SHA-256 published by the vendor. Mismatches trigger an incident alert. (3) **Mitigation (if no vendor attestation available):** The institution performs an annual firmware-integrity audit: the HSM vendor provides a signed statement that the firmware version deployed matches the released version and has not been modified. The statement is countersigned by an independent auditor. (4) **Residual risk:** If firmware attestation is unavailable and the HSM vendor is compromised, the chain's signature becomes repudiable — the institution cannot prove the signature was generated by the bank's signing key vs by the attacker. The institution documents this residual in its INCD coordination procedures and plans firmware-attestation adoption or HSM-vendor switching if the risk threshold is exceeded."

### Q-4. SDK build reproducibility — can an Israeli bank confirm the SDK binary matches the source?

Herald.Py SDK source is published on GitHub (Apache 2.0). But the SDK ships as a pip package (Python) or a JAR (Java) or a binary (Go). An INCD concern: did the pip/JAR/binary come from the source published on GitHub, or did the vendor inject supply-chain-poisoned code during the build? The spec does NOT address SDK-side reproducible builds. Herald.Py should publish SHA-256 hashes of the released packages with a GPG signature so a Tal-like adversary can confirm they match. **Ask:** Add to supply-chain.md: "SDK reproducible-build commitment: (1) Herald.Py publishes SHA-256 hashes of all released SDK packages (pip, JAR, wheel, binary) alongside GPG signatures from the Herald.Py release-signing key. (2) An institution can download the source, build locally, compare SHA-256 against the published hash. Match confirms the binary is unmodified. (3) If an institution or independent auditor detects a SHA-256 mismatch, the incident is escalated to the FFIEC working group and the vendor. (4) The release-signing GPG key is held by [list of authorized signers at Herald]. Key rotation is published with an expiration timeline. (5) The vendor commits to providing this assurance for every release for the lifetime of the product; sunsetting this commitment is a protocol-version change requiring regulator approval."

### Q-5. Hourly seals vs daily seals — is the spec flexible on cadence for nation-state threat models?

The spec §4.2 defines a daily Merkle seal cadence (UTC midnight). This gives a 24-hour detection window for tampering after the seal is signed. Against a nation-state APT with 18 months of persistence, detecting at 24 hours is excellent. But an INCD red-team exercise might ask: what if you detect tampering at 4 hours into the day? Recovery still requires 20 hours to complete the seal cycle. Institutions with higher threat tolerance (Tier-1 banks processing correspondent payments) would want hourly seals to bound detection to 1 hour and recovery to 2 hours. The spec does not forbid hourly seals, but does not explicitly enable them. **Ask:** Add to spec §4.2: "Seal cadence is daily at the default (UTC tenant-day boundary). Institutions MAY adopt hourly seals with INCD or regulator approval. Hourly seals increase HSM operational cost but reduce detection latency to < 1 hour for any in-day tampering. The spec's threat model, verifier procedure (§7), and incident-response playbook are cadence-agnostic; hourly seals require only a configuration change (cadence parameter) and an HSM-capacity assessment. Institutions document their chosen cadence in CC8.1 and align it with their threat model (daily for community banks, hourly for tier-1 or high-value operations)."

### Q-6. Nation-state threat model — does the spec acknowledge Israel's threat landscape?

The spec's threat model (09-threat-model.md) describes adversary capabilities (A through I: external wire attacker, insider with database access, HSM physical compromise, etc.). But the threat model is written for a US banking context: the most severe adversary is an insider with database access plus the signing key (Adversary C/D), followed by application-process compromise (Adversary E/F). The INCD threat model reorders the severity: assume a nation-state actor with 18 months of persistence inside the bank's network, capable of: (1) compromising the HSM firmware (not just physical access, but supply-chain injection), (2) exfiltrating the signing key if the HSM is network-connected, (3) poisoning the OTLP collector or the SDK via supply-chain attacks, (4) forging chain entries retroactively if they gain access to the IKM. The spec does NOT name this threat model. **Ask:** Add to threat-model.md a section "Nation-state threat model (INCD-aligned for Israeli banks)": "(1) The INCD threat model assumes a capable nation-state adversary (e.g., Iran IRGC cyber, Lazarus-equivalent operators) can compromise the bank's infrastructure within 18 months. The bank is not defending against theoretical break-ins; it is assuming the bank is already compromised. (2) Against this threat model, the chain's value is not preventing tampering (which a compromised bank cannot prevent), but detecting and proving tampering occurred. The HSM signature is the integrity anchor: even if the IKM is exfiltrated, the attacker must compromise the HSM firmware to re-sign a forged history. (3) The chain's design (separation of duties, cryptographic binding, append-only storage, independent verification) is sound against this threat model. But institutional controls must supplement: firmware attestation, vendor-compromise detection, supply-chain discipline, INCD coordination. (4) An INCD red-team exercise tests: if the red team compromises the SDK, the OTLP collector, and the HSM firmware simultaneously, can they forge a chain entry and sign it under the bank's key? The spec's design answers 'only with simultaneous compromise of three independent components; any one component's integrity failure is detected.' The institution's job is to make simultaneous compromise detectable via monitoring and incident response."

### Q-7. PPL Amendment 13 cross-border transfer rules — can an Israeli bank's chain data leave Israel?

Israel's Privacy Protection Law Amendment 13 (August 2025) is stricter than GDPR on cross-border transfers of AI-related data. The law treats AI inference logs and AI-generated decisions as "sensitive personal information" (similar to biometric or genetic data). The rule: Israeli data controllers cannot transfer sensitive personal information to any country outside Israel without explicit Privacy Protection Authority (PPA) approval. The spec's vendor-hosted topology (§6.3) allows multi-tenant vendor cloud in the US or EU. An Israeli bank using vendor-hosted Herald.Compliance would have all chain events (tokens, even if de-identified) stored outside Israel. Under PPL Amendment 13, this is likely non-compliant without PPA approval. **Ask:** Add to regulator-pack or privacy-by-design.md: "PPL Amendment 13 compliance for Israeli deployment: (1) **Domestic storage requirement:** Israeli-controlled banks deploying the chain MUST ensure all chain data (ledger, seal records, tokens) remain physically stored in Israeli jurisdiction. This rules out US or EU cloud for production. (2) **Compliant topologies:** (a) Self-hosted in Israeli data center or colocation facility. (b) Vendor-hosted in Israel-only cloud (e.g., AWS Tel Aviv region or Azure Israel region if available). (c) Vendor-hosted in US/EU cloud only if the vendor submits and the institution obtains PPA approval for cross-border transfer; approval typically requires SCC + supplementary safeguards (encryption key held by bank, vendor cannot decrypt). (3) **Privacy-store custody:** The token-to-PII mapping MUST remain in Israeli jurisdiction under all circumstances; it cannot be replicated to off-shore backup. (4) **INCD coordination:** For cross-border transfer arrangements, the institution notifies the INCD as part of its Directive 361 cyber-risk management program."

### Q-8. Incident-response playbook — does Scenario 4 (master-key compromise) align with Israel's Cyber Defense Law?

Israel's Cyber Defense Law 5778-2018 (חוק הגנה סייבר) mandates notification to the INCD for "computer-security incidents" affecting critical infrastructure (which includes banking). The notification clock is not explicitly stated in the law (unlike the FFIEC's 36-hour rule); institutions coordinate with the INCD based on incident severity. The spec's incident-response playbook (Scenario 4: "Master-key compromise or suspected compromise") names a 36-hour FFIEC clock. For Israeli banks subject to both Cyber Defense Law and FFIEC, what is the correct clock? **Ask:** Add to incident-response-playbook.md Scenario 4 or a new section "Multi-regulator incident-notification for Israeli banks": "(1) **Israeli banks subject to both Cyber Defense Law 5778 and FFIEC oversight (those with USD correspondent accounts):** When a master-key compromise is suspected, the institution notifies both regulators simultaneously. (2) **Notification clock:** Use the faster clock. For most Israeli cyber incidents, the INCD clock is 'immediately upon determination, no later than 24 hours.' The FFIEC clock is 36 hours. Israeli banks notify BOTH the INCD and the primary FFIEC regulator within 24 hours. (3) **Content alignment:** The notification to the INCD (per Cyber Defense Law) names the incident, the affected systems, and the preliminary impact assessment. The notification to the FFIEC is the formal computer-security incident notice. Both describe the same incident; the timeline and format differ per each regulator's requirements. (4) **INCD coordination procedure (institutional responsibility):** The institution designates a Cyber Defense Liaison to the INCD; the liaison is the initial contact point for incident reporting. The institution's IR playbook names the liaison's contact procedure and escalation path to INCD duty officers."

### Q-9. Vendor-selection criteria — what should an Israeli bank ask Herald before deployment?

The spec names vendor-hosted topology as conformant (§6.3). But an Israeli bank using a vendor is dependent on the vendor's cyber posture. INCD Directive 357 (third-party cyber risk) requires the institution to assess the vendor before onboarding and to monitor the vendor's control maturity. The spec does not name vendor-selection criteria. An Israeli bank would ask Herald: (1) Where do you keep the HSM? (2) Can you provide HSM firmware-attestation certificates? (3) Is your build reproducible and independently auditable? (4) Do you have a formal INCD coordination procedure for incidents? The spec should guide institutions on what to ask. **Ask:** Add to vendor-hosted-controls.md or regulator-pack/vendor-selection.md: "Vendor-selection criteria for Israeli deployment: (1) **HSM custody:** Vendor confirms the HSM is in Israeli jurisdiction (Israeli data center or Israeli government-approved facility). Vendor provides HSM audit logs (read-only). (2) **Firmware attestation:** Vendor provides quarterly firmware-integrity attestations signed by an independent auditor (or HSM vendor-supplied attestation if available). Institution spot-checks via cryptographic verification. (3) **Build reproducibility:** Vendor publishes SDK and ledger source code (Apache 2.0 or equivalent); vendor provides SHA-256 hashes of released binaries signed with a GPG key. Institution can rebuild locally and verify match. (4) **Incident-response SLA:** Vendor commits to INCD notification within 24 hours of incident determination (aligned with Cyber Defense Law). Vendor provides a dedicated incident-response contact for the institution. (5) **Access controls:** Vendor names which vendor employees have access to the HSM, the OTLP collector, and the ledger server. Institution reviews quarterly; any access changes trigger an audit. (6) **INCD coordination:** Vendor designates a Cyber Defense Liaison and coordinates with the INCD on cyber-incident policy. Vendor confirms no conflict with Israeli national security policy (e.g., vendor is not subject to US CFIUS restrictions that would prevent Israel cooperation). (7) **Contract:**Agreement names these criteria as binding service-level obligations. Failure to meet any criterion is grounds for immediate termination."

### Q-10. Key rotation under compromise — can the chain recover if the IKM is exfiltrated?

The spec (10.10 and threat-model.md R2) addresses key rotation as the response to suspected master-key compromise. The procedure: issue a new `key_version`, derive a new session key from the new IKM, and start signing entries with the new key. Past entries remain verifiable against the old key. But the INCD threat model asks: if an APT exfiltrated the old IKM (and we don't know for how long they had it), how confident are we that the new key is uncompromised? The spec assumes key rotation is sufficient; the INCD would ask: is there a delay after rotation before we trust new entries? **Ask:** Add to incident-response-playbook.md Scenario 4 or spec §10.10: "Key rotation recovery and re-attestation: (1) Upon suspected master-key compromise, the institution immediately rotates the IKM (generates a new key_version, deploys to the HSM). (2) Events captured after rotation use the new key and are initially considered 'under re-attestation' — they are integrity-bearing but may be subject to re-verification if the new key is later discovered to be compromised. (3) **Re-attestation period (configurable):** The institution defines a period (e.g., 7 days or 30 days) during which entries using the new key are treated as 'high confidence, pending full attestation.' After the period, if no further compromise indicators emerge, the entries transition to 'fully attested' and are eligible for compliance and regulatory evidence. (4) **Institution's INCD coordination:** The institution notifies the INCD of the rotation and the re-attestation period. The INCD may recommend additional monitoring or forensic evidence gathering. (5) **Examiner expectations:** During an FFIEC examination, if the examiner asks about entries captured in the re-attestation window post-rotation, the institution discloses the rotation timeline and the re-attestation status. The examiner assesses whether the entries support the control's integrity claim given the compromise-recovery context."

### Q-11. Verifier supply-chain discipline — is the verifier a black box or auditable?

The spec §2.4 (00-overview.md) claims the verifier is the integrity anchor: the examiner runs it offline, the verifier makes no network calls, the binary is signed twice (cosign + GPG manifest), and the public key is registered with the regulator. But an INCD threat model includes: what if the verifier binary is substituted with a backdoored version that silently passes forged chains? The spec names defenses (cosign, GPG, reproducible builds) but does not clarify whether an Israeli institution can audit the verifier source and rebuild it locally, or whether they are dependent on the published binary. **Ask:** Add to supply-chain.md or design/07-verifier-supply-chain.md: "Verifier auditing and local rebuild: (1) The verifier source code is published at [GitHub URL] under Apache 2.0. (2) An institution or independent auditor can download the source, review the code, and rebuild locally: `bash build.sh --release --all` produces the verifier binary. (3) The rebuilt binary's SHA-256 is compared against the published binary's SHA-256. Match confirms the binary is unmodified from the source. (4) The build process is fully deterministic: no external fetches, no auto-updates, pinned stdlib and dependency versions. (5) If an institution detects a SHA-256 mismatch (local rebuild ≠ published), the institution immediately escalates to [FFIEC/working group] as a supply-chain compromise event. (6) The reference implementation (Go) documents the exact build command, the pinned Go version, and the expected SHA-256. Conforming verifiers in other languages MUST support local rebuild and provide SHA-256 reproducibility guarantees."

### Q-12. Detection speed under HSM compromise — is 24 hours fast enough?

The spec §4.2.2 defines a daily seal cadence. An HSM-side attacker who gains access to the signing key could forge any new seal going forward. Detection happens at the next day's seal: the recomputed root doesn't match the signed root. So detection latency is 24 hours in the worst case (attacker compromises HSM at 00:01, forges seals for 24 hours, detection at 24:01 when the verifier recomputes and fails). Against a nation-state APT planning to be inside for 18 months, 24-hour detection is good. But is it good enough for an Israeli bank processing high-value correspondent payments? The spec does NOT analyze this trade-off or enable faster cadence for higher-risk workloads. **Ask:** Add to spec §4.2 or §6.5: "Seal cadence and detection-latency trade-offs: (1) **Daily (default):** 24-hour detection window for HSM-side tampering. Appropriate for most workloads. HSM operational cost is minimal. (2) **Hourly (optional, requires INCD or regulator approval):** 1-hour detection window for HSM-side tampering. Appropriate for tier-1 institutions processing high-value decisions or correspondent payments. HSM operational cost is ~24x daily cost. (3) **Configurable per workload:** Institutions MAY apply daily cadence to routine decisions and hourly cadence to payment-authorization decisions. The institution documents the cadence choice in CC8.1. (4) **Recovery time:** Detection latency and recovery time are distinct. Even with hourly detection, recovery (key rotation, forensic analysis, re-verification) takes hours to days. The spec's incident-response playbook (Scenario 4) covers recovery procedures independent of cadence."

### Q-13. INCD red-team exercise — how does the chain perform under simultaneous supply-chain compromise?

The INCD conducts annual red-team exercises (cyber defense drills) for tier-1 banks. A typical scenario: red team compromises the SDK, the OTLP collector, and the HSM firmware simultaneously. Can they forge a chain entry and have it sign under the bank's key? The spec's design is: even with all three components compromised, the verifier can detect the forgery IF at least one component is still under the bank's control (e.g., if the bank re-verifies the entry against the public key). But the spec does NOT name INCD coordination procedures or readiness criteria. **Ask:** Add to incident-response-playbook.md or a new section "INCD red-team readiness": "(1) **Red-team scenario:** INCD red team simulates simultaneous compromise of SDK + OTLP collector + HSM firmware. Can they produce a verifying chain entry signed under the bank's key? (2) **Expected outcome:** No. The red team can produce forged entries, but the verifier (which is independently held by the bank and the regulator) will reject them as non-conformant (invalid signature, Merkle root mismatch, etc.). (3) **Institutional readiness:** Before the INCD red-team exercise, the institution confirms: (a) the verifier binary is held securely (air-gapped, independently rebuilt), (b) the public key is registered with the bank and the regulator, (c) the institution has a daily verification run (sample-checking entries against the public key) to detect forged signatures, (d) incident-response procedures are live and testable. (4) **Post-exercise:** The institution and the INCD analyze the exercise results. If the verifier successfully detected all forged entries, the exercise is a pass. The exercise report is filed with the Bank of Israel as evidence of cyber-resilience under nation-state threat model."

### Q-14. PPL Amendment 13 — AI inference logs as personal data, what does the privacy-store need to comply?

PPL Amendment 13 §1 defines "AI-related decisions" as personal data. An AI-decision log entry (decision, reasoning, model version, inputs, output) is personal data when it describes an identifiable individual. The spec's privacy-by-design approach (tokenize PII before capture) reduces identifiability but does NOT eliminate the risk: the privacy-store mapping (token-to-original) still exists and links tokens back to identities. Under PPL Amendment 13, the privacy-store is a high-risk processing activity. The spec does NOT address PPL Amendment 13's specific requirements. **Ask:** Add to privacy-by-design.md or a new `14-ppl-amendment-13.md`: "**PPL Amendment 13 compliance for Israeli AI-decision logging:** (1) **Personal data definition:** AI-decision logs are personal data under PPL §1 when they describe identifiable individuals. Even tokenized entries are personal data if the token-to-original mapping exists. (2) **Purpose specification:** The institution's published policy specifies the purpose (fairness audit, customer disputes, regulatory examination, litigation defense). Purpose creep (e.g., using the chain for marketing targeting) is prohibited. (3) **Lawful basis:** Israeli law does not use GDPR's Article 6 framework, but PPL requires a lawful reason. For banks, the lawful bases are: (a) legal obligation (Banking Regulation, FFIEC requirements), (b) explicit consent from the customer (if GDPR-equivalent consent is collected), (c) legitimate interests (fairness audit). The institution documents the basis in its privacy policy. (4) **Privacy-store custody:** The token-to-PII mapping MUST remain in Israeli jurisdiction (PPL Amendment 13 §2). Cross-border transfer is prohibited without PPA approval. The mapping MUST be encrypted at rest (PPL §5 security requirement). The mapping MUST be deleted at the end of the retention period or immediately upon customer request (PPL §3 right to erasure). (5) **Access controls:** Only designated personnel (privacy team, customer service for disputes) access the privacy-store. Access logs MUST be retained for 1 year (PPL §5 audit requirement). (6) **Transparency:** Customers MUST be notified that their AI-decision logs are retained for the stated purpose (PPL §4 notification requirement). Notification happens at the time of the decision (e.g., loan approval notice discloses 'your decision is logged for fairness audit for 7 years'). (7) **Data subject rights:** Customers have the right to access (PPL §5), rectify (PPL §3), erase (PPL §3), and object to processing (PPL §6). The institution's procedure provides these rights within 30 days of request (PPL §5 timeline). (8) **Incident notification:** If the privacy-store is breached, the institution notifies the Privacy Protection Authority within 48 hours and affected individuals within 60 days (PPL §7). (9) **Annual audit:** The institution's DPA reviews PPL Amendment 13 compliance annually and updates procedures as Privacy Protection Authority guidance evolves."

### Q-15. IKM custody under Directive 361 — can the IKM be in cloud KMS or must it be on-prem HSM?

Bank of Israel Directive 361 §6 requires "master key custody in accordance with international best practices." The spec allows cloud HSM (AWS CloudHSM, Azure Dedicated HSM) and on-prem HSM. But Directive 361 does NOT explicitly allow cloud-based key custody; it references "international best practices" which Israeli banks interpret as on-prem or exclusive cloud custody (not shared multi-tenant cloud). An Israeli bank's compliance officer might question whether AWS CloudHSM is Directive 361-compliant. **Ask:** Add to regulator-pack or a note to spec §10.5: "Directive 361 §6 and cloud HSM compliance for Israeli banks: (1) **Conformant HSM tiers per spec §10.5:** AWS CloudHSM (dedicated single-tenant), Azure Dedicated HSM (dedicated single-tenant), on-prem Thales/Entrust/Utimaco HSM. (2) **Non-conformant for Directive 361:** AWS KMS (shared multi-tenant), Azure Key Vault Standard (shared multi-tenant). These are crypto-as-a-service, not HSM-based. (3) **Israeli bank guidance:** Directive 361 §6 requires exclusive key custody (the bank is the only party with access to the IKM). Dedicated cloud HSM meets this criterion if the contract explicitly forbids the cloud provider from accessing the key. The institution documents the exclusive-custody claim in its CC8.1 control description. (4) **Audit criteria:** Bank of Israel examiners verify the cloud HSM contract and the HSM audit logs confirming no vendor-side key operations occurred during the audit period."

### Q-16. Merkle root re-computation — can an adversary trick the verifier into accepting a forged root by forging both the root AND the chain?

The spec §7 step 10 (Merkle verification) recomputes the root from the chain entries and compares against the signed root. If an insider with database access and the IKM forges 100 entries mid-day and re-computes the Merkle root, both the entries and the root change consistently. The verifier's root recomputation matches the forged root (because the verifier computed it from the same forged entries). The signature check passes (because the attacker signed the forged root). Only the daily seal from *yesterday* (which was signed before the tampering) proves the root has changed. **Ask:** Confirm in spec §7 or negative test vectors that this scenario is covered: "Test case N024: Attacker forges 10 entries mid-day, recomputes Merkle root, signs the forged root with a copy of the signing key extracted from the HSM. Verifier outcome: (a) if the verifier is given only the forged chain + the forged signature (no prior day's seal), the verifier cannot detect the forgery (the root recomputation matches, the signature is valid). (b) The detection requires cross-day linkage: the verifier checks that today's root Merkle-chains to yesterday's root via some structural property (e.g., inclusion proof). If the forged root breaks the chain-to-yesterday, detection succeeds. (c) If no cross-day linkage is specified, the verifier is vulnerable to this scenario even with HSM signature, and the spec should document it explicitly as a residual risk: an attacker with both database access AND the signing key can forge an entire day's history if no external witness (prior day's seal) is available."

### Q-17. Audit procedure P-6 (key reconciliation) — does weekly frequency catch an exfiltration within 7 days?

The spec audit-procedures.md P-6 (Key fingerprint reconciliation) runs weekly. The procedure: the institution recomputes the SHA-256(tenant_id || IKM) and compares to the recorded key_fingerprint on each chain entry. A mismatch indicates cross-tenant key swap or a key-version inconsistency. But the INCD threat model includes: what if the IKM is exfiltrated on a Monday, and the attacker uses the exfiltrated key to forge entries all week, then the weekly reconciliation runs on Friday and detects the mismatch? The institution has already lost 4 days of evidence. The question: is weekly frequency sufficient, or should it be daily for tier-1 banks? **Ask:** Add to audit-procedures.md P-6: "Key fingerprint reconciliation frequency and detection latency: (1) **Default cadence:** Weekly. Sufficient for most institutions; detects key compromise within 7 days. (2) **Recommended for tier-1 banks under INCD threat model:** Daily. Reduces detection latency to 24 hours. (3) **High-security option:** Continuous (automated daily or on-demand). Institution runs reconciliation every time a new key_version is deployed or on demand if a compromise is suspected. (4) **Institution choice:** Documented in CC8.1. The cadence is a risk-level decision; institutions processing high-value operations (correspondent payments, regulatory decisions) SHOULD adopt at least daily cadence."

### Q-18. Threat-model residual R3 (DFA / fault-injection) — what does an Israeli bank do if a DFA attack is suspected?

Threat-model.md R3 acknowledges differential-fault-attack (DFA) residual risk: FIPS 140-2 L3 certifies physical tamper-resistance but NOT DFA resistance. If an APT uses side-channel fault-injection against the HSM to extract the signing key, the chain's integrity collapses. The spec documents the risk but does NOT name incident-response procedures. An Israeli bank subject to INCD red-team exercises might be tested on DFA recovery. **Ask:** Add to incident-response-playbook.md a new Scenario 16 ("HSM DFA attack suspected or confirmed"): "(1) **Detection trigger:** The institution's security team observes anomalous HSM power patterns, unusual network traffic to the HSM, or physical evidence of tampering (seal broken, network cable inserted in unexpected way). (2) **Initial response:** Isolate the HSM immediately (disconnect network, disable power if safe). Preserve HSM physical state for forensic examination. (3) **Assessment:** The institution engages the HSM vendor and an independent cryptographic forensics firm to assess whether a DFA attack is plausible given the observed evidence. (4) **Incident classification:** If DFA is confirmed or highly plausible, escalate to MRIA (Matters Requiring Immediate Attention). (5) **Recovery:** (a) Generate a new signing keypair on a clean, uncompromised HSM (or on-prem. (b) Notify the regulator and the INCD within 24 hours (per Cyber Defense Law). (c) Re-sign all seals from the potentially compromised HSM using the new key. (d) The institution's verifier must be updated to accept both the old key (for historical validation, with a caveat that entries may be repudiable) and the new key (for current entries). (e) Invalidate all entries signed by the compromised HSM for regulatory evidence purposes; treat them as 'forensically questionable, pending investigation.' (6) **Documentation:** The institution documents the incident in the INCD coordination file and coordinates with the INCD on recovery timeline."

### Q-19. Examiner access to the HSM signing key — should Bank of Israel hold a copy?

The spec's normal posture: the institution holds the HSM signing key; the examiner holds the public key for verification. But the INCD threat model includes: what if the institution itself is compromised and lies to the regulator about whether tampering occurred? The INCD might ask: should the Bank of Israel or the INCD hold a secondary copy of the signing key so they can independently re-sign and verify? This is a major policy decision (shared key custody breaks the separation-of-duties principle), but it's worth asking. **Ask:** Add a note to regulator-pack/policy-considerations.md: "Shared HSM signing key custody (policy question for FFIEC/INCD): (1) **Current posture:** The institution holds the signing key; the examiner/regulator holds the public key. This is the separation-of-duties standard. (2) **Alternative (high-trust-threshold):** The institution and the Bank of Israel/INCD each hold a copy of the signing key under separate HSM custody. Signing requires m-of-n authorization (e.g., 2-of-2: institution + INCD must both approve the daily seal signing). (3) **Pro:** If the institution is compromised, the INCD can independently verify that the daily seal was legitimately signed. (4) **Con:** (a) Operational complexity: 2-of-2 signing adds latency and failure modes. (b) Governance: shared key custody is a major escalation of examiner authority and may not align with Israeli banking law. (c) Key compromise risk doubles: two HSMs at two locations = two failure points. (5) **Israeli-specific consideration:** Directive 361 §6 emphasizes institutional key custody; recommending shared custody would require a policy update to Directive 361. This is a working-group-level decision, not a spec issue."

### Q-20. Cross-border correspondent banking — does the chain protect against Iran-sanction-violation risk?

An Israeli bank processing USD correspondent banking must comply with US Iran sanctions and OFAC rules. If an Iranian entity infiltrates the bank's systems and alters decision logic to approve transfers to Iran-linked accounts, the chain captures evidence of the AI decision. But does the chain help the bank prove "we didn't intentionally approve sanctions violations" or does it make the bank liable ("you had a chain and still failed to detect")? The spec does NOT address sanctions-compliance interaction with the chain. **Ask:** Add to regulator-pack/use-cases.md or a new section "Sanctions compliance and the chain": "(1) **Use case:** An Israeli bank processing USD correspondent payments uses the chain to log all payment-authorization decisions. If the AI system approves a payment to a sanctioned entity (due to compromise or misconfiguration), the chain provides forensic evidence: model inputs, decision reasoning, timestamp. (2) **Regulatory benefit:** The bank can demonstrate to OFAC/FinCEN investigators that it had an integrity-bearing audit trail, that the decision was reviewed by the model at timestamp X, and that the compromise/misconfiguration occurred at timestamp Y. This supports the bank's defense in a sanctions-violation investigation. (3) **Limitation:** The chain does NOT prevent sanctions violations. The bank still needs upstream controls (sanctions-list checking, model fairness testing) and downstream controls (payment-system auditing). The chain is the evidence, not the prevention. (4) **Documentation:** The institution's sanctions-compliance policy should name the chain as part of the evidence-collection procedures for sanctions-violation investigations."

### Q-21. Multi-language verifier implementations — are they cryptographically sound?

The spec is language-agnostic: the verifier can be implemented in Go, Python, Rust, Java, etc. But cryptographic implementations have language-specific pitfalls (Go's constant-time compare vs Python's timing side-channels, Rust's memory-safety vs C's buffer overflows). The spec does NOT name a conformance test for multi-language implementations. An Israeli bank might want a Python verifier (runs on internal Linux infrastructure) but be concerned that a Python implementation of HMAC-SHA-256 is less hardened against side-channel attacks than Go. **Ask:** Add to spec §10.8 or supply-chain.md: "Multi-language verifier implementations and cryptographic assurance: (1) The verifier's cryptographic primitives (HMAC-SHA-256, SHA-256, Ed25519) MUST use standard-library implementations for the target language (Go's crypto, Python's cryptography library, Java's BouncyCastle, Rust's RustCrypto). (2) Implementations MUST pass the same conformance corpus (test vectors 001–016, N001–N023) byte-for-byte. (3) Implementations MUST implement constant-time comparison for HMAC and key-fingerprint checks (§10.8). Language-specific timing-safe libraries: Go's crypto/subtle.ConstantTimeCompare, Python's hmac.compare_digest, Java's MessageDigest with loop-invariant timing, Rust's subtle crate. (4) Institutions deploying a verifier in a non-Go language SHOULD have the implementation independently reviewed by a cryptographic auditor before production use. (5) The FFIEC working group MAY maintain a registry of independently-audited verifier implementations in each language, published alongside the reference Go implementation."

### Q-22. Verifier regression testing — how does an Israeli bank detect if a new verifier version has a bug that silently passes forged entries?

A new version of the verifier is released with a bug: it skips step 9 (MAC check) under certain conditions. The bug is subtle and the test suite doesn't catch it. A bank deploys the new verifier version. An attacker's forged entries pass verification when they shouldn't. The spec does NOT name continuous regression testing procedures. **Ask:** Add to supply-chain.md or audit-procedures.md: "Verifier regression testing and multi-version running: (1) **Regression suite:** Every new verifier release includes a regression test against the full conformance corpus (test vectors 001–016, N001–N023). The test suite is published with the release; institutions can run it before deploying. (2) **Multi-version canary:** Before deploying a new verifier version to production, the institution runs both the old and new verifiers against a sample of the chain (e.g., 1000 recent entries). Both verifiers must produce identical PASS/FAIL outcomes. If they diverge (old version PASS, new version FAIL, or vice versa), the new version is not deployed until the divergence is investigated. (3) **Continuous regression (optional for tier-1 banks):** The institution maintains two independently-implemented verifiers (e.g., Go + Python, or Go + Rust). The institution periodically runs both on the same chain data and compares outputs. Divergence triggers an investigation. This is defense-in-depth against implementation bugs in a single verifier."

### Q-23. Recovery from HSM hardware failure — what's the operational playbook?

The spec §4.2 (late-binding events) addresses the case where the HSM is unavailable during seal-signing. But what's the full operational playbook if the HSM hardware fails and is unavailable for 3 days? Can the bank continue to capture and HMAC-chain events? Can the bank substitute a backup HSM for sealing? The spec does NOT detail recovery procedures. **Ask:** Add to incident-response-playbook.md a new Scenario 17 ("HSM hardware failure and recovery"): "(1) **Detection:** The daily seal job attempts to sign and the HSM is unresponsive (network timeout, HSM not responding to heartbeat). (2) **Initial response:** The institution's IT ops team initiates the HSM failure runbook. (a) Check HSM network connectivity. (b) Check HSM power (if on-prem). (c) Contact the HSM vendor (AWS, Azure, or on-prem support) with the HSM serial number and fault code. (3) **Interim operations:** (a) The SDK continues to capture and HMAC-chain events (the per-event HMAC is independent of the HSM). (b) Events are buffered in the ledger with a 'pending_seal' flag. (c) The institution notifies the Bank of Israel and the INCD that the seal job is delayed; provides an ETA for HSM restoration. (4) **Recovery (single HSM):** When the HSM is back online, the seal job re-runs and produces the accumulated Merkle root for all pending events. The seal record is timestamped with the actual signing time (not the UTC midnight it was supposed to sign). (5) **Failover (HSM redundancy):** If the institution has a backup HSM (standby) in a different data center, failover is immediate: the backup HSM is activated, events are re-routed to the backup, and sealing continues without interruption. The backup HSM must hold a copy of the signing key (under separate HSM custody protocols). (6) **Post-recovery:** The institution investigates the root cause of the HSM failure and implements preventive maintenance. The seal delay and the recovery procedure are documented in the incident file and reported to the Bank of Israel."

### Q-24. PPL Amendment 13 — Privacy Protection Authority enforcement posture and audit triggers

Israel's Privacy Protection Authority (PPA) is the data-protection regulator (equivalent to an EU DPA). The PPA has enforcement authority and can levy administrative fines up to 5% of global turnover. The spec does NOT address PPA audit risk. An Israeli bank should understand: what triggers a PPA audit of the chain, and what are the compliance penalties for non-conformance? **Ask:** Add to regulator-pack or privacy-by-design.md: "Privacy Protection Authority (PPA) audit triggers and enforcement: (1) **Audit triggers for AI-decision logging systems:** (a) Customer complaints about automated decision-making (PPL §3 right to human review). (b) Data-subject requests for access or erasure (PPL §3) that institutions fail to fulfill within 30 days. (c) Incident notifications of privacy-store breaches (PPL §7 breach notification). (d) Random audits: the PPA conducts periodic examinations of critical-sector organizations (banks fall in this category). (2) **Enforcement posture:** The PPA may issue directives to cease or modify processing if it determines the processing violates PPL §1-§7. Failure to comply is an administrative fine of up to 5% of global turnover (PPL §12). For a large Israeli bank, this can be tens of millions of shekels. (3) **Compliance checklist:** The institution's annual DPA review assesses: (a) Is the privacy-store encrypted at rest and in Israeli jurisdiction? (b) Are customer notification and consent procedures documented and followed? (c) Are data-subject rights (access, erasure, rectification) fulfilled within 30 days? (d) Are breaches detected and notified within 48 hours to the PPA? (e) Are access logs retained and auditable? (4) **PPA examination preparation:** If the PPA initiates an audit, the institution must produce: (a) Privacy policy and notices (customer-facing). (b) Data Processing Agreement (DPA) with any vendor. (c) Breach notification logs for the past 3 years. (d) Access logs for the privacy-store. (e) Incident reports and remediation plans. ## Closing assessment

**Partial?** No.

Tal files no Partial. The spec is cryptographically sound and operationally defensible. The three identified gaps (supply-chain compromise detection, persistence-latency analysis, PPL Amendment 13 rules) are **manageable through institutional compensating controls** and do not represent spec defects. An Israeli bank can deploy the chain responsibly by: (1) self-hosting the ledger and verifier, (2) implementing vendor-compromise detection via build reproducibility and verifier supply-chain discipline, (3) running hourly seals if the HSM vendor supports it, (4) operating a documented INCD coordination program for incident response and red-team exercises. With these compensating controls, the chain is a net positive for cyber-resilience under the INCD threat model.

**Confidence under Bank of Israel Directive 361 + PPL Amendment 13.** High confidence, with conditions. The spec's cryptographic design (HMAC chain + daily Merkle seal + HSM Ed25519 signature) is sound against Directive 361 threat model (insider database access, key compromise, vendor subversion). The spec's tokenization approach (privacy-by-design.md) satisfies PPL Amendment 13's requirements if the privacy-store remains in Israeli jurisdiction and access-controlled. The spec's documentation (audit-procedures.md P-1 through P-10, incident-response-playbook.md Scenarios 1-15) aligns with FFIEC examination standards and provides a foundation for Bank of Israel examination procedures. The gaps (supply-chain discipline, vendor-selection criteria, INCD coordination procedures) are organizational discipline, not technical defects; institutions with mature cyber-risk programs can operationalize them.

**Confidence is conditional on institutional execution:** (1) Israeli banks MUST self-host or negotiate INCD-compliant vendor terms (rules out commodity US/EU cloud storage). (2) Institutions MUST implement verifier supply-chain discipline (build reproducibility, SHA-256 verification, independent audit of non-Go implementations). **Recommended next steps.**
