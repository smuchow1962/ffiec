## Headline

The spec is cryptographically well-grounded and operationally sound. The threat model is clearly articulated, the primitives are standard (HMAC-SHA-256, HKDF-SHA-256, Ed25519, RFC 6962 Merkle), and the test vectors cover structural attacks comprehensively. **Reuven's read pass found 26 places where the spec's cryptographic claims require formal clarification, proof-obligation articulation, or threat-model completion.** None of these are design defects; most are proof-obligation gaps that an IETF CFRG reviewer would file in standards-track review. The spec is at submission quality for FFIEC working group approval; these questions refine its cryptographic maturity for academic citation, IRTF reference, and regulator-defense contexts.

**What the spec does well cryptographically.** The primitive choices are conservative and standard. HMAC-SHA-256 has rigorous EUF-CMA security under widely accepted assumptions. HKDF (RFC 5869) is the gold standard for key derivation. RFC 6962 Merkle with explicit leaf/internal-node domain separation prevents the classic second-preimage attack. Ed25519 is broadly deployed and well-analyzed. The threat model's adversary catalog (A-I) is comprehensive on first read. The negative test corpus covers structural-attack scenarios broadly. The reference implementation is open-source under Apache 2.0, enabling academic and industry review.

**What the spec needs for academic citation.** Explicit security definitions in standard cryptographic terminology (EUF-CMA, second-preimage resistance, IND-CPA explicit non-claim). A formalized adversary capability matrix (what each adversary controls vs observes vs can query). Proof-obligation articulation for compositional security across the three layers (per-event MAC, per-day Merkle, per-day HSM signature). Explicit non-claims (forward secrecy, IND-CPA confidentiality) that prevent consumer misinterpretation. Side-channel and fault-injection resistance requirements named explicitly per implementation guidance.

Each question below is a one-paragraph gap. The closing is a procedural or documentary recommendation — a paragraph of spec text, a threat-model addendum, a test-vector extension, or an informative cryptographic note grounded in FIPS / NIST / RFC citations.

## Supporting questions

### Q-1. Formal security definition — existential unforgeability under chosen-message attack

The spec claims the HMAC chain "proves tampering is detectable." Formally, this should be stated as: the per-event MAC provides **existential unforgeability under chosen-message attack (EUF-CMA)** per FIPS 198-1. The spec does not explicitly invoke EUF-CMA, which means auditors must infer the security goal from the construction. **Ask:** Add a "Security definitions" section to Spec §1 naming EUF-CMA for the MAC, second-preimage resistance for Merkle, and EUF-CMA for the Ed25519 signature, citing FIPS 198-1, RFC 6962, and FIPS 186-5 respectively. The section should explicitly state what each primitive does NOT claim: the MAC provides no confidentiality (data is not encrypted); Merkle provides no collision resistance (only second-preimage); the HSM signature provides no forward secrecy (rotation does not erase past session keys from memory).

### Q-2. HKDF info parameter uniqueness enforcement — cross-tenant collision risk

The spec binds `tenant_id` into the HKDF info parameter per §4.1: `info_for_tenant = HKDF_INFO_BASE || "|" || utf8(tenant_id)`. Security depends on uniqueness of the info string across all derivations. If two operators independently choose the same `tenant_id`, they will derive identical session keys, violating the per-tenant isolation guarantee. The spec (§10.1) requires "tenant_id MUST be unique per institution," but does not specify uniqueness enforcement: institutional discipline (SOC audit trail), cryptographic enforcement (a content-addressable registry), or policy only. **Ask:** Add to §10.1 or §4.1.2: "Uniqueness of `tenant_id` values is enforced at the IKM-registry layer. The registration process MUST reject a `tenant_id` that is already registered for the institution. For multi-tenant SaaS vendors serving multiple institutions on a shared platform, the IKM registry MUST enforce uniqueness globally across (institution, tenant_id) pairs. Implementations that permit duplicate `tenant_id` values under the same institution are non-conformant."

### Q-3. HKDF salt reuse across tenants — NIST SP 800-56C alignment

The spec uses a global constant `HKDF_SALT = b"ffiec.chain-of-custody.v1.salt"` across all tenants. Combined with per-tenant `info_for_tenant`, the construction is theoretically sound under random-oracle modeling, but NIST SP 800-56C KDF recommendations suggest salt should vary with context. The spec's posture is static-salt + context-dependent-info; an explicit justification would benefit IETF CFRG review. **Ask:** Add an informative note to §4.1: "The HKDF-SHA-256 construction per RFC 5869 uses a static salt constant and per-tenant info binding. This is compliant with NIST SP 800-56C §5.4 (HKDF is an approved KDF), which requires salt and context to jointly ensure independence of derived keys. The per-tenant `info` parameter provides the required context separation; the static salt is acceptable because (a) the salt is a public constant (not secret), and (b) the info parameter is unique per tenant. An alternative design using per-tenant salts is more conservative and may be considered for v1.x."

### Q-4. 128-bit truncated key fingerprint — birthday-bound attack surface

The `key_fingerprint = SHA-256(utf8(tenant_id) || ikm)[:16]` truncates SHA-256 to 16 bytes (128 bits). For collision attacks, the birthday bound is 2^64 — within reach for a tier-1 deployment over a 7-year retention window in adversarial scenarios. The spec uses the fingerprint for operational audit (P-6 reconciliation) and verifier pre-flight (§7 step 8), not for cryptographic security — but the design choice warrants articulation. **Ask:** Add to §1.2 or §10.6: "The `key_fingerprint` is a 16-byte public identity binding used for operational audit, not cryptographic security. The truncation to 128 bits is acceptable because the fingerprint is checked by the verifier BEFORE any MAC computation; an attacker cannot exploit a birthday collision because a collision would require simultaneously presenting two different IKMs as if they were the same, which the verifier detects via the per-entry MAC check. For cryptographic properties depending on collision resistance, the full 32-byte SHA-256 output is used (Merkle leaf hashing, `hkdf_inputs_digest`). The 128-bit fingerprint is sized for human-readable operational audit and forensic familiarity with 16-byte identifiers; institutions with extreme-scale deployments (petabyte-scale ledgers over multi-decade retention) may consider the full 32-byte fingerprint as a v1.x option."

### Q-5. Ed25519 strict canonicalization and signature malleability

RFC 8032 §8.4 (Strict canonicalization) addresses Ed25519 signature malleability: some implementations permit multiple canonical forms of a valid signature. The spec requires Ed25519 (FIPS 186-5, which references RFC 8032) but does not specify whether strict canonicalization is enforced. A non-strict implementation could accept multiple signatures for the same root, complicating forensic evidence and admitting signature-malleability cross-implementation interop bugs. **Ask:** Add to §4.3: "The HSM signature MUST use strict canonicalization per RFC 8032 §8.4 to prevent signature malleability. Implementations using cryptographic libraries that permit non-strict Ed25519 signatures MUST add explicit rejection of non-canonical forms (e.g., by re-encoding the signature and comparing to the received bytes before acceptance). The FIPS 186-5 standard references RFC 8032; the spec's Ed25519 requirement is interpreted as the strict form. Most FIPS-validated HSMs already enforce strict canonicalization; the requirement is also applicable to verifier-side parsing."

### Q-6. Merkle second-preimage resistance — property distinction

RFC 6962 Merkle trees are vulnerable to second-preimage attacks if the leaf and internal-node hashing are indistinguishable. The spec §4.2 uses RFC 6962's leaf-prefix (0x00) and node-prefix (0x01) scheme, which is correct. However, the spec does not explicitly state that **second-preimage resistance** (not collision resistance) is the load-bearing property. This matters because SHA-256 is believed secure against second-preimage attacks even if collisions were found; the distinction informs algorithm-rollover triggers. **Ask:** Add to §4.2 (Merkle seal): "The daily Merkle seal depends on second-preimage resistance of SHA-256 (RFC 6962), not collision resistance. An attacker cannot find a different set of events that produce the same Merkle root. The leaf-prefix (0x00) and node-prefix (0x01) scheme per RFC 6962 §2.1 ensures an internal node cannot be presented as a leaf; this prevents trivial second-preimage attacks. SHA-256 is believed secure against practical second-preimage attacks; if a second-preimage attack on SHA-256 is demonstrated, a spec patch with SHA-3 migration (or successor per NIST guidance) would be required."

### Q-7. Length-extension vulnerability surface — SHA-256 in Merkle leaf construction

SHA-256 is vulnerable to length-extension attacks (given `SHA-256(m)`, an attacker can compute `SHA-256(m || padding || m')` without knowing `m`). The spec's Merkle leaf uses `SHA-256(0x00 || payload_hash)`, which is safe (the 0x00 prefix is a domain separator). But the spec does not explicitly document the length-extension analysis or rule out other call sites. **Ask:** Add an informative section auditing all SHA-256 call sites for length-extension: "(1) Merkle leaf: `SHA-256(0x00 || payload_hash)` is safe; the domain-separator prefix prevents length extension. (2) Merkle internal node: `SHA-256(0x01 || left || right)` is safe; the domain-separator prefix prevents confusion with leaf nodes. (3) Fingerprint: `SHA-256(utf8(tenant_id) || ikm)[:16]` is safe; the SHA-256 output is truncated. (4) `hkdf_inputs_digest`: `SHA-256(salt || info || length_LE32)` is safe; HKDF-Expand uses HMAC-SHA-256 which is length-extension-resistant. (5) Empty-day Merkle root: `SHA-256("")` is the RFC 6962 convention; no length-extension surface. All SHA-256 uses are either domain-separated, truncated, or wrapped in HMAC; no raw SHA-256 is applied to attacker-controlled unbounded data."

### Q-8. Layered authentication compositionality — joint security claim

The spec uses three layers: (1) per-entry HMAC-SHA-256, (2) daily Merkle seal, (3) HSM Ed25519 signature. Is their composition formally secure? The spec does not provide a compositional security argument. Informally, the layers are independent (an attack on one does not simplify others), but a formal model would strengthen the claim for academic citation. **Ask:** Add an informative section "Compositional security" to §1 or design/01-primitives-spec.md: "The three authentication layers are independent: (a) HMAC-SHA-256 at capture proves no wire-level tampering after emission; (b) daily Merkle seal proves no retroactive entry insertion, deletion, or reordering after ingest; (c) HSM signature proves the Merkle root was sealed by the institution's key without unauthorized modification. The composition is secure under standard assumptions (SHA-256 and HMAC hardness, second-preimage resistance, Ed25519 hardness) because an attacker who breaks one layer must simultaneously forge or break a second layer. The composition provides defense-in-depth — a single-layer compromise is insufficient to silently tamper. A formal game-based proof of compositionality is beyond v1.0; the informal argument provides auditor confidence, and future versions may add a TLA+ or Tamarin protocol model."

### Q-9. Session-key leakage and IKM minimum-length grounding

The spec requires IKM ≥ 32 bytes (§10.6) and asserts the public per-entry `key_fingerprint` is not offline-grindable. This is correct under modern compute (2^256 brute force is infeasible) but the spec does not cite the RFC 4868 justification or NIST SP 800-132 guidance on key-stretching. **Ask:** Add to §10.6: "The IKM minimum of 32 bytes (256 bits) is grounded in RFC 4868 (HMAC-SHA-256 keying recommendations) and NIST SP 800-132 (password-based key derivation). A 32-byte IKM provides 256-bit strength; a 16-byte IKM (128-bit) is below the cryptographic security level of SHA-256 and is non-conformant. The per-entry `key_fingerprint` is not brute-forceable under the 32-byte IKM: an offline attacker observing fingerprints from a chain cannot reverse-engineer the IKM via brute force (the search space is 2^256, infeasible). An attacker with online access to the HKDF derivation function (e.g., via a compromised HSM or KMS) could attempt key enumeration; this is why the spec requires HSM custody (FIPS 140-2 L3 or higher) and rate-limiting per implementation guidance."

### Q-10. Dual-algorithm transitional security definition — one-out-of-two vs AND-security

Section 4.3.2 introduces dual-algorithm (Ed25519 + post-quantum, e.g., Dilithium) posture for v1.x. The spec does not define the security model: is the requirement (a) **one-out-of-two** (signature is valid if Ed25519 OR post-quantum is valid) or (b) **AND-security** (both must be valid)? These have radically different security properties. AND-security is conservative; one-out-of-two is weaker. **Ask:** Add to §4.3.2: "The dual-algorithm transition posture for v1.x will follow AND-security semantics: a seal record's signature is valid ONLY if all algorithms listed in the `signatures` array verify successfully. This is conservative: an attacker must forge both Ed25519 and Dilithium signatures. The one-out-of-two model is rejected because it would permit an attacker to break the weaker algorithm and forge seals. Algorithm retirement (when Ed25519 is finally deprecated) requires a transition period where legacy seals are verified under Ed25519 alone; new seals require post-quantum algorithms only."

### Q-11. Constant-time comparison enforcement — implementation pitfall

The spec §10.7 names constant-time comparison for fingerprint and MAC checks and cites stdlib functions. This is good practice but enforcement is left to implementations. The spec should clarify whether timing-attack resistance is a normative MUST or operational SHOULD. **Ask:** Clarify spec §10.7: "Implementations MUST use constant-time comparison for the `key_fingerprint` check (§7 step 8) and the `payload_hash` MAC verification (§7 step 9). Use of byte-by-byte comparison, string equality, or other non-constant-time primitives is non-conformant and exposes the verifier to timing attacks. For languages without stdlib constant-time helpers, the implementation must provide constant-time comparison as part of the SDK. The implementation's security documentation MUST commit to constant-time comparison and describe the mitigation mechanism."

### Q-12. Forward secrecy absence — explicit non-claim

The spec provides no forward secrecy: if the IKM is compromised, all past session keys can be recomputed (HKDF derivation is deterministic). This is by design, but the spec does not explicitly state that forward secrecy is not provided, which could mislead consumers into assuming session-key compromise is bounded. **Ask:** Add to §1.2 (Epistemic scope): "The chain does not provide forward secrecy for session keys. HKDF derivation is deterministic from the IKM; if the IKM is compromised, an attacker can recompute any past session key for that tenant and forge past events that would verify correctly. However, the chain's integral design makes this attack detectable: a compromised IKM is typically detected (via fingerprint mismatches, operational anomalies, incident response), and the Merkle seal and HSM signature cover the events as they were captured and sealed; retroactive forgery requires backdating, which modifies the seal timestamp or sign_payload, both of which are covered by the Ed25519 signature. The absence of forward secrecy is a known property, not a vulnerability. For institutions requiring session-key forward secrecy, a v1.x extension could introduce per-process ephemeral DH or HKDF-based key ratcheting."

### Q-13. Replay attack prevention — cross-tenant and cross-institution boundaries

Can an event captured for Tenant A be replayed at Tenant B? The HKDF info parameter prevents the MAC from verifying, but is there a wire-level path where the event lands in B's chain before MAC verification rejects it? The spec's threat model does not explicitly address replay. **Ask:** Add to threat model §2 or verifier §7: "Replay attacks are prevented at two layers: (1) the per-tenant session key (derived from tenant_id in HKDF info) ensures an event captured under Tenant A's MAC cannot verify under Tenant B's key; (2) the verifier's step 4 (cross-chain lift detection) rejects entries whose `tenant_id` does not match the file's header `tenant_id`. An attacker who injects a Tenant-A event into a Tenant-B chain will see MAC verification fail at step 9, or tenant_id mismatch fail at step 4. An attacker who replays a Tenant-A event at a different time in the same chain would see chain-link breakage at step 6 (prev_hash does not match). Replay across institutions is structurally prevented because each institution has a separate IKM registry and a separate verifier."

### Q-14. RNG requirements and seeding — no explicit spec commitment

The spec requires FIPS 140-2 L3 HSMs for signing but does not specify entropy sources for IKM generation or initial handshake randomness. An institution using a weak RNG for IKM generation defeats the entire design. **Ask:** Add a new section §10.X: "IKM Generation Requirements — The IKM MUST be generated from a FIPS-validated cryptographic random-number generator (FIPS 140-1/-2/-3 approved per NIST SP 800-90A). For HSM-based IKM custody, the HSM's internal RNG is acceptable if the HSM has FIPS 140-2 L3+ validation. For software-based IKM generation, the institution MUST use an OS-level CSPRNG (e.g., /dev/urandom on Linux, CryptGenRandom on Windows, or SecureRandom in language standard libraries). IKM generation using weak sources (e.g., system time, sequential counters, hash of configuration files) is non-conformant. Implementations SHOULD provide explicit RNG-source configuration and logging via operational events; a `master_key.generated` event should include the RNG type for audit-trail completeness."

### Q-15. HMAC-SHA-256 size match against key length

RFC 2104 specifies HMAC construction with keys smaller or larger than the hash block size. The spec uses 32-byte (256-bit) session keys, shorter than SHA-256's 512-bit block size. This is correct (RFC 2104 handles short keys via padding) but the spec does not explicitly confirm. **Ask:** Add an informative note to §4.1: "The session key is 32 bytes (256 bits), per HKDF-SHA-256 output. This is shorter than SHA-256's internal block size (512 bits), so HMAC-SHA-256 pads the key per RFC 2104 §2. The keyed MAC has full 256-bit security (the output length, not the key length, determines HMAC security per FIPS 198-1). The 32-byte key length is aligned with RFC 4868 recommendations for HMAC-SHA-256 keying."

### Q-16. Verifier output authenticity — no meta-cryptography for the verifier itself

The verifier is a software tool that outputs `PASS` or `FAIL`. The spec does not specify how to authenticate the verifier output itself (Diego's Q-10 asks about meta-evidence; Reuven's question is cryptographic). Can the verifier output be forged? The spec does not require the verifier to produce a cryptographically signed output. **Ask:** Add to §7 or design/07-verifier-design.md: "The verifier's output (PASS/FAIL + reason string) is written to stdout and is not cryptographically signed; the institution's incident-response procedures require the output to be captured and preserved as evidence. Auditors verify the verifier binary via cosign and reproducible-build validation. For institutions requiring cryptographic attestation of verifier output (high-assurance scenarios), a future v1.x extension could add an optional `--sign-output` mode where the verifier writes a detached Ed25519 signature alongside the output. For v1.0, verifier-output authenticity is established through binary-provenance verification (cosign) and reproducible-build testing, not through output-level signing."

### Q-17. Negative-test cryptographic-attack coverage — gap analysis

The test-vector corpus includes N001-N023 negative cases covering structural attacks (reordering, bit-flips, signature forgery). But they do NOT cover cryptographic-attack scenarios: (a) length extension on a Merkle leaf, (b) Ed25519 signature malleability, (c) HKDF info collision, (d) birthday-bound Merkle collision documentation. These are not bugs (the spec is correct), but test-vector coverage is silent. **Ask:** Add to design/08-test-vectors.md a cryptographic-attacks subsection: "Recommended future test cases: (1) Merkle length-extension variant (replace 0x00 prefix with null, verify rejection) — validates the domain-separator defense; (2) non-strict Ed25519 signature (if using non-RFC-8032-strict implementations) — validates strict canonicalization; (3) HKDF info collision (manually forge two entries with same tenant_id to the same session key, verify fingerprint mismatch catches it) — validates per-tenant isolation; (4) conceptual Merkle collision scenario (document the birthday bound and confirm no practical attacks exist for v1.0's scale). These cases are not critical for v1.0 (the spec is correct), but they close the cryptographic-attack test surface for academic citations."

### Q-18. Algorithm agility for per-entry MAC — missing in v1.0

The seal record has an explicit algorithm identifier, allowing future signature-algorithm migration. But per-entry MACs use implicit `"HMAC-SHA-256"` with no version field. If SHA-256 weakens, all v1.0 entries are affected and no per-event algorithm negotiation is possible. **Ask:** Add to §4.1 or design/05-otlp-wire.md: "The per-entry HMAC algorithm is implicitly HMAC-SHA-256 in v1.0. A future v1.1 or v2.0 could add an optional `ffiec.chain.algorithm` attribute (defaulting to `"HMAC-SHA-256"` for v1.0 entries, allowing `"HMAC-SHA-3"` or `"HMAC-BLAKE3"` for future entries). This is recommended but not critical for v1.0 because (a) per-entry algorithm negotiation adds operational complexity, and (b) if SHA-256 weakens, the spec working group will issue an emergency patch requiring migration of all v1.0 entries to a new format/algorithm within 90 days."

### Q-19. HKDF-Expand vs HKDF-Extract — completeness of the Model B handshake

The spec uses HKDF-SHA-256 (which includes both Extract and Expand per RFC 5869). But Model B (HSM-resident PRK) extracts in the HSM and expands in the SDK. If the PRK is exposed in transit, it could be used to derive past session keys (though only for that tenant). The spec does not discuss whether the PRK is a load-bearing secret. **Ask:** Add to §4.1.2 (Model B HSM capability note): "In Model B with HSM-resident PRK, the PRK (pseudorandom key, 32 bytes) is the output of HKDF-Extract and the input to HKDF-Expand. If the PRK is exposed in transit, an attacker can derive the same session keys as the SDK for that tenant and subsequent handshakes, but the attacker cannot recover the IKM or derive session keys for other tenants. The PRK in transit MUST be protected by the confidential channel (mTLS per §4.1.2 authentication requirement), not by cryptographic secrecy. This is compliant with NIST SP 800-56C (KDFs assume authenticated, confidential transport of intermediate values)."

### Q-20. Merkle root computation for empty days — alternative-construction analysis

The empty-day convention (SHA-256("") for a day with zero events) is per RFC 6962 §2.1. The spec locks this in. But is there a collision risk if the same root appears for multiple empty days? The answer is no (every empty day produces the same root by design), but the spec could clarify the intentional-collision posture. **Ask:** Add to §4.2: "Empty days produce a deterministic Merkle root `SHA-256("")` per RFC 6962. Multiple empty days produce the same root, which is intentional and correct. The root does not serve as a day identifier; the seal record's `seal_date` identifies the day. The identical empty-day root across different days is not a collision risk because it is deterministic and expected, the seal record binds the root together with the date (the date is part of sign_payload per §4.3), and each day's seal is independently signed. An attacker cannot present an empty day from 2026-05-06 as if it were 2026-05-07 without also forging the signature."

### Q-21. Per-tenant determinism property — testable definition

The spec asserts "per-tenant determinism" (§4.1.3 property 4). This is testable, and audit procedure P-3 tests it. But the spec does not formalize what "byte-identical" means in the presence of implementations with different RNG or floating-point libraries. **Ask:** Add to §4.1.3: "Per-tenant determinism means HKDF-SHA-256 produces the same 32-byte session key for the same (IKM, salt, info, length) inputs. This is a property of RFC 5869, not an additional requirement. HKDF uses only SHA-256 and concatenation; no randomization or floating-point arithmetic is involved. Therefore, `HKDF-SHA-256(ikm, salt=HKDF_SALT, info=info_for_tenant, length=32)` produces the same bytes across any two implementations that correctly implement RFC 5869. The test-vector corpus provides byte-exact expected values; non-determinism indicates a non-conformant implementation."

### Q-22. Adversary capability matrix — formal precision

The threat model names Adversaries A through I with capability descriptions. But the spec does not formalize capabilities in a matrix (read access, write access, network position, key access, oracle access). An IETF CFRG reviewer would ask for an explicit capability grid. **Ask:** Create a new §2.1 (Adversary capability matrix) in threat-model.md with a table:

| Adversary | Read ledger | Write ledger | Network position | IKM access | HSM access | Session-key access | Oracle access |
|---|---|---|---|---|---|---|---|
| A (external wire) | No | No | Yes (wire) | No | No | No | No |
| B (database insider) | Yes | Yes | No | No | No | No | No |
| C (operational insider) | Yes | No | No | No | Yes | No | Limited |
| D (HSM physical) | No | No | No | No | Yes (physical) | No | Limited |
| E (process compromise) | Limited | No | No | No | No | Yes | Yes |
| F (vendor subversion) | Partial | Partial | No | No | No | Partial | Partial |
| G (supply-chain compromise) | Partial | Partial | No | No | No | Partial | Partial |
| H (examiner-time tooling) | Yes | No | No | Limited | No | No | Partial |
| I (time-source attacker) | No | No | Yes (NTP) | No | No | No | Yes |

This matrix makes the threat model's structural logic explicit and helps auditors reason about coverage.

### Q-23. Constant security-level assumption — implicit but not stated

The HMAC-SHA-256 provides 256-bit output (128-bit security level against birthday attacks). The Merkle uses SHA-256 (128-bit security level against second-preimage attacks). Ed25519 provides ~128-bit security. The effective security level is the minimum: 128-bit. The spec does not state this explicitly, which could mislead consumers into thinking the chain provides 256-bit security. **Ask:** Add to Spec §1: "The chain's effective security level is 128 bits, determined by the weakest layer: Ed25519 (128-bit security) and HMAC-SHA-256 birthday-bound (2^128 attempts). This is compliant with NIST's current recommendation of 128-bit security for cryptographic systems processing non-classified government information (NIST SP 800-175B). Institutions requiring 256-bit security (post-quantum or extremely long retention horizons) should consider v1.x extensions introducing Dilithium (256-bit security) and SHA-3 (256-bit preimage resistance). For v1.0, the 128-bit security level is appropriate for FFIEC banking regulation, which assumes a 7-year retention horizon and adversaries constrained by practical computation limits."

### Q-24. Institutional uniqueness enforcement gaps — multi-instance IKM collision

If an institution operates multiple deployments (on-prem + cloud, or multiple cloud regions), could two deployments accidentally generate identical `tenant_id` values? The spec requires uniqueness but does not specify enforcement at cross-deployment boundaries. **Ask:** Add to §10.1: "Multi-deployment institutions MUST maintain a single, global IKM registry (not per-region or per-instance). The registry MUST enforce `tenant_id` uniqueness across all deployments. Acceptable implementations: (1) a centralized registry service (e.g., AWS Secrets Manager shared across regions), (2) a database shared across regions with uniqueness constraint, (3) a documented procedure where the central team approves all `tenant_id` allocations before any deployment uses them. Institutions that permit independent `tenant_id` generation in each deployment and allow duplicates across deployments are non-conformant. For cloud-native topologies using managed KMS, the KMS's multi-region replication provides automatic consistency; the institution need only document the KMS as the authoritative registry."

### Q-25. Fault-injection attack on HSM — residual risk and mitigation

The threat model (§2.4 HSM physical attack) names this as residual risk. Fault injection (deliberately inducing timing errors to leak keys) is a practical attack against some HSMs. The spec does not require FIA (fault-injection attack) countermeasures. **Ask:** Add to §10.3 or threat model §2.4 (residual risks): "Fault-injection attacks (differential fault attacks, DFA) against HSM signing operations are a known vulnerability class on some hardware implementations. FIPS 140-2 L3 devices are not required to certify DFA resistance; FIPS 140-3 does require DFA resistance for certain algorithms per SP 800-108. The spec accepts the residual risk of DFA compromising the HSM; an institution's incident-response procedure (IR Scenario 4: HSM key compromise) covers detection and recovery. Institutions deploying in jurisdictions with threat models including nation-state attackers SHOULD select HSMs with documented DFA countermeasures. For v1.0, the assumption is that FIPS 140-2 L3 physical tamper-resistance is sufficient for the threat model's baseline."

### Q-26. RFC 8785 JCS stability assumption — canonicalization dependencies

The spec requires RFC 8785 JSON Canonical Serialization for the canonical bytes. The spec does not discuss what happens if future versions of RFC 8785 are published with clarifications or bug fixes. Does the spec lock to RFC 8785 published in 2020, or to "RFC 8785 as currently published"? **Ask:** Add to §5: "The canonical form MUST conform to RFC 8785 (JSON Canonical Serialization) as published in January 2020 (or any RFC 8785 clarifications that do not change the serialized output). The `hkdf_inputs_digest` is computed from the HKDF inputs and MUST be consistent with the running canonical-form constants per spec §4.1; a future RFC 8785 clarification that changes the canonical representation would require a spec patch updating `hkdf_inputs_digest` and `format_version`. Institutions are encouraged to test their JCS implementations against the `008-jcs-edge-cases/` test corpus to validate compliance independent of RFC version."
