## Headline

The spec is in good shape. The byte-level contract is mostly resolved by the reference test vectors — vector 001 pins down the single-event positive case, 008 (the JCS-edge-cases fixture) handles RFC 8785 nuances, the negative N-vectors lock the verifier's failure-mode taxonomy. **Aanya's read pass found 28 places where the spec text on its own is ambiguous and the test vectors are the only normative anchor.** That's fine for a v1.0 ship — the vectors are the conformance contract — but it means a future spec editor who edits the prose without re-running the vectors can drift away from the reference. Each question below is a one-paragraph close: a sentence in the spec text, a fixture extension, or a clarifying note.

The spec's strength as observed: every property the reviewer needed to verify was eventually pinned by either text or vector. The spec's weakness: the text leans on the vectors as the source of truth in 28 named places, and that coupling is not itself documented. Round-13 should make the spec/vector relationship explicit ("the test vectors are normative; their byte-exact outputs are the conformance contract; spec text describes the algorithm, the vectors pin the bytes") so that future maintainers see the relationship as deliberate, not accidental.

## Supporting questions

### Q-1. HKDF `info` parameter — UTF-8 encoding boundary made explicit?

Spec §4.1 says `info_for_tenant = HKDF_INFO_BASE || b"|" || utf8(tenant_id)`. The test-vector README confirms `||` is byte concatenation, the separator is the byte `0x7C`, and `utf8(tenant_id)` is the UTF-8 encoding of the string. The text is clear when read with cryptographic-protocol fluency, but the boundary between "string literal" and "UTF-8 encoding" is implicit. A maintainer reviewing this prose in two years might not immediately see that `utf8(tenant_id)` for a tenant id containing non-ASCII codepoints (a `cn:` prefix in CJK locales, accented Latin in EU deployments) is the byte sequence of the UTF-8 encoding, not a percent-encoded or escape-formatted string. **Ask:** add a non-ASCII tenant_id to a test vector (e.g., `"tenant-日本語-prod"` or `"tenant-müller-eu"`) with the corresponding `info_for_tenant` hex pinned in the fixture; alternatively, a one-sentence clarification in §4.1 ("`utf8(tenant_id)` is the raw UTF-8 byte encoding of the string; no percent-encoding or escaping is applied").

### Q-2. Merkle tree non-power-of-2 leaf count — RFC 6962 §2.1 exactly, or a variant?

Spec §4.2 says "odd-leaf trees MUST be balanced by promoting the unpaired leaf to the next level (the same scheme used by RFC 6962)." RFC 6962 §2.1 right-promotes the unpaired rightmost leaf at each level. The test vectors cover small leaf counts (single event = single leaf, multi-event-same-run = small number of leaves), but a non-power-of-2 leaf count test (e.g., 3 leaves, 5 leaves, 7 leaves) was not visible in the corpus Aanya read. A future implementation that re-hashes the unpaired leaf rather than promoting it produces a different root for any leaf count not a power of 2. **Ask:** add a test vector — perhaps a future `003-multi-run-same-day` or `007-ten-thousand-events` — that exercises an odd leaf count (3, 5, 7, or larger prime). Pin the resulting `merkle_root` hex. The reference Go source resolves the question; the spec text + vectors should as well.

### Q-3. Hex encoding case-sensitivity in `sign_payload` — lowercase only?

Spec §4.3 shows `hex(merkle_root)` and `hex(hkdf_inputs_digest)` in the `sign_payload` text. The test vectors show these as lowercase hex. The spec does not state "lowercase only" explicitly; it relies on the vectors to pin the case. A maintainer editing the spec without re-running vectors might not notice; a future v1.x extension that introduces a new hex-encoded field in `sign_payload` could ship with uppercase hex without any text-level red flag, breaking signature reproducibility. **Ask:** add a one-sentence normative statement in §4.3 after the `sign_payload` definition: "All hex-encoded values within `sign_payload` MUST use lowercase ASCII digits and lowercase a-f; uppercase hex is non-conformant and produces a different signature." A negative test vector that signs with uppercase hex and confirms the signature differs would also work.

### Q-4. Line termination in `sign_payload` — LF only, never CRLF, on every platform?

Spec §4.3 shows `sign_payload = "ffiec.chain-of-custody.v1\n" || ...`. The test vectors confirm `0x0A` between fields. The spec does not explicitly forbid CRLF (`0x0D 0x0A`) or clarify that implementations producing seal records on Windows hosts must emit `0x0A` only. The bytes go into the Ed25519 signature; line-ending choice breaks reproducibility cross-platform, and a Windows-hosted reference implementation could subtly diverge from a Linux-hosted one if the prose isn't explicit. **Ask:** add a conformance note in §4.3: "All line terminations in `sign_payload` are the single byte `0x0A` (LF / ASCII newline), never `0x0D 0x0A` (CRLF). Implementations on every platform MUST emit `0x0A` when computing `sign_payload`. Platform-default newline conversion in serialization libraries (e.g., Go's `text/template`) MUST be disabled on this hot path." One sentence prevents a class of cross-platform divergence.

### Q-5. Trailing newline in `sign_payload` — present after the final field, or omitted?

Spec §4.3's pseudocode shows the last field as `hex(hkdf_inputs_digest) || "\n"`, which suggests a trailing newline is part of the structure. The test vectors decode `sign_payload_single_hex` to text ending after `hkdf_inputs_digest` — but whether the byte sequence ends with `0x0A` or stops at the last hex digit is genuinely ambiguous from the rendered text alone. A maintainer who reads "the final line" as "the line that doesn't need terminating" (the convention in some text protocols) could subtly remove the trailing newline. **Ask:** make the structure unambiguous in §4.3 — either rewrite as `... || hkdf_inputs_digest_hex || "\n"` (every line, including the last, terminated with `\n`), or as `... || hkdf_inputs_digest_hex` (no trailing newline). Then add a sentence: "There is no additional terminator after the structure; the byte length of `sign_payload` is exactly the sum of its fields plus the line terminators shown."

### Q-6. Verifier failure-reason string grammar — normative byte-for-byte, or semantically equivalent?

Spec §7 lists 12 ordered steps, each with expected failure modes. Negative test vectors specify expected reason strings (e.g., `"payload_hash MAC mismatch at seq N"`, `"chain link broken at seq N"`). The spec uses prose ("the verifier reports..."); the test vector descriptions imply the reason strings must match byte-for-byte. A future verifier might emit `"MAC mismatch at entry 1"` (synonyms, different separator), pass the spirit, and fail the byte-exact contract. The current state forces examiners to interpret reason strings; a normative grammar would make the comparison mechanical. **Ask:** add to spec §7 or to the test-vector README: "Verifier failure-reason strings are normative byte-for-byte. A verifier that produces semantically equivalent but textually different strings is non-conformant. The expected reason strings in each negative test vector are the conformance reference." Optionally provide a regex grammar per failure step so implementers can validate in their own test harnesses.

### Q-7. `key_fingerprint` truncation — Python slice notation in normative text?

Spec §4.1 defines `key_fingerprint = SHA-256(utf8(tenant_id) || ikm)[:16]`. The bracket notation `[:16]` is Python slice syntax for "first 16 bytes." Go uses `[:16]` too in slice expressions, but other languages don't (Rust uses `&hash[..16]`, JavaScript/TypeScript uses `.slice(0, 16)` or `.subarray(0, 16)`). The test vectors pin the expected output as 32 hex chars / 16 bytes, so the meaning is recoverable. But the spec text is normative across languages and the Python-specific slice notation is a small but unnecessary coupling. **Ask:** rephrase as "the first 16 bytes of the SHA-256 output" or "SHA-256(...)[0:16] (the leading 16 bytes of the 32-byte hash output)." The vectors don't change; only the prose is more language-neutral.

### Q-8. Canonical JSON — RFC 8785 binding strict, or profile-relaxed?

Spec §5 says "MUST follow RFC 8785" for canonical form. RFC 8785 has no formal profiles, but JCS implementations differ in how strictly they enforce NaN/Infinity rejection, how deeply they recurse, and how they handle trailing whitespace tolerance. Test vector 008 exercises RFC 8785 edge cases (floats, Unicode, surrogate pairs, NaN/Infinity rejection, key ordering) and the README states 008 is part of the conformance bar. The spec text doesn't explicitly elevate 008 to MUST; it's prose-level guidance. **Ask:** add a normative statement in §5 or §8: "Implementations MUST pass every case in test-vector 008 (`rfc-8785-edge-cases`). Failure on any case in 008 means the implementation is non-conformant for v1.0, even if it passes 001–007 and 010–015. The edge cases are load-bearing: they prove the canonical-form property at the boundaries where naive JCS implementations diverge."

### Q-9. JCS numeric precision for floats — full IEEE-754 double range, or a safer subset?

RFC 8785 §3.2.2.3 follows ECMAScript Number-to-String. Test vector 008 includes cases near `Number.MAX_SAFE_INTEGER` (2^53−1) and cases beyond (where round-trip fidelity is lost in IEEE-754 doubles). For the chain's purposes the practical concern is: AI-system outputs include token-count integers (small, safe) and timing measurements (small floats). But an LLM could emit a hallucinated number outside the safe-integer range, the application could capture it verbatim, and the canonical form's stability depends on RFC 8785's float-string algorithm being reproduced byte-for-byte. **Ask:** confirm in §5 (or §8) that the full IEEE-754 double range is supported and that test 008's float cases are normative for the boundary. If there are practical limits the spec wants to impose (e.g., reject NaN/Infinity, accept all finite doubles), name them in §5 explicitly so a future maintainer doesn't accidentally narrow them.

### Q-10. Pre-flight `hkdf_inputs_digest` mismatch — security boundary, or operator misconfiguration?

Spec §7 step 2 says the verifier "asserts the file's `hkdf_inputs_digest` against the running FFIEC constants" and "rejects the file if the digest does not match." Negative N010 (`header-hkdf-digest-flipped`) confirms this as a hard failure. But the spec doesn't disambiguate the *meaning* of a mismatch: is it (a) a different institution's chain (an adversary supplied an unrelated file), (b) a vendor in non-FFIEC posture (vendor-flag mode running with different HKDF constants), or (c) a misconfiguration (the verifier was built with stale constants)? The diagnostic the examiner sees doesn't help discriminate. **Ask:** clarify §7 step 2's reason text: "A mismatched `hkdf_inputs_digest` indicates the file was produced under different HKDF constants. The verifier rejects under `--strict`. The institution's IR procedure (Scenario X in `incident-response-playbook.md`) names the response: confirm the verifier's running constants match the institution's posture, then re-verify; if the file is genuinely a non-FFIEC artifact, route to vendor-flag analysis." This bounds the operator-side response.

### Q-11. Empty-day Merkle root — explicitly named?

Spec §4.2 and the test-vector README state that for a tenant-day with zero events, `merkle_root = SHA-256(b"")` (the SHA-256 hash of an empty byte string), pinned at `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855`. The vectors resolve this. The spec text says only "construct a binary Merkle tree over the `payload_hash` of every event" — a reader unfamiliar with RFC 6962's empty-tree convention might not realize an empty tree has a canonical root. **Ask:** add to spec §4.2: "For a tenant-day with zero events, the Merkle root is `SHA-256(b'')` (the SHA-256 of an empty byte sequence) = `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855`. This is consistent with RFC 6962 §2.1's definition of the empty-tree root and with the daily-seal cadence (§4.2.1) that requires a seal even on zero-activity days."

### Q-12. Streaming Merkle vs in-memory — both conformant, or only one?

Spec §7 does not mandate a Merkle implementation strategy. The conformance test (test-vector README) requires a verifier that "computes `merkle_root` over each chain's ordered `payload_hash` values per RFC 6962" — silent on whether the implementation streams (constant memory) or builds the tree in memory. Tier-1 institutions need streaming for cost reasons (Maya's Q-7 raises this from the operations side); a clean-room v1.x implementer needs to know the contract. **Ask:** add a note to §7 or §8: "The Merkle root MUST be reproducible from the ordered leaf sequence; implementations are free to use streaming or in-memory tree construction, provided the final root matches the test-vector expectation byte-for-byte. Both strategies are conformant. The reference implementation may choose either; the conformance contract is the root, not the construction." This unblocks tier-1 implementations without loosening the contract.

### Q-13. Cross-run chain linking within a day — separate chains, or chained together?

Spec §4.1 says each run starts with `seq=1` and `prev_hash = 32 zero bytes`. The spec also says events are ordered by `(run_id, seq)` ascending for the Merkle seal. But the spec doesn't explicitly state whether two runs in the same tenant-day share a chain (run 2's first event's `prev_hash` references run 1's last `payload_hash`) or are isolated chains (run 2's first event's `prev_hash = 0x00...0x00`). Test vector 002 covers single-run multi-event; the cross-run case is unaddressed in vectors. **Ask:** clarify in §4.1 that "Each run is an independent chain. Run 2's first event has `prev_hash = b'\\0' * 32` regardless of run 1's last `payload_hash`. The Merkle seal aggregates `payload_hash` values across all runs in the tenant-day in `(run_id, seq)` ordering, but the chain links (`prev_hash`) do not cross run boundaries." Or, if the design is the opposite, state that. Add a future test vector `003-multi-run-same-day` to pin the bytes.

### Q-14. `format_version` mismatch — minor-version compatibility posture?

Negative test vectors N008 (entry-level mismatch) and N009 (header-level mismatch) cover the case where a v1.0 verifier sees `format_version = "v2"`. They expect different reason strings. But there's no test case for minor-version variants like `format_version = "v1.1"` or `format_version = "v1.0"` (full semver). The spec §7 step 1 says "refuses unrecognized values most-specific-first" — implying exact-match required. A future v1.1 spec edit could ship without disturbing v1.0 verifiers, *if* the compat posture is "v1.0 verifiers refuse any string not exactly equal to `v1`." Or the posture could be "v1.0 verifiers accept v1.x as compatible." **Ask:** add a test vector for `format_version = "v1.1"` and pin the v1.0 verifier's expected outcome (presumably reject with `"format_version v1.1 not supported by this verifier (running v1)"`). Add a sentence to §7 step 1: "Format-version values are compared for exact equality. A v1.0 verifier accepts only `format_version = 'v1'`. v1.x extensions that reuse the v1 format string MUST be wire-compatible at the byte level; v1.x extensions that change the wire format MUST use a different format-version value."

### Q-15. Canonical-bytes scope — circular reference between `payload_hash` and the canonical form?

Spec §4.1 property 7 says "The canonical bytes that go into the MAC MUST exclude every field listed in the per-entry stamp table." The stamp table includes `payload_hash` itself, `prev_hash`, `key_version`, `key_fingerprint`, `format_version`. A reader implementing this for the first time might compute the canonical form, observe that `payload_hash` is part of the entry, exclude it (correctly), and then realize `prev_hash` is also excluded (which is intuitive once stated but not obvious). **Ask:** clarify in §4.1 property 7: "The MAC input is the canonical JSON of the event's *application content* — the OTel-namespace and `audit.*`-namespace attributes the application emitted. The chain stamps the entry with `prev_hash`, `payload_hash`, `key_version`, `key_fingerprint`, and `format_version` as a separate layer; these stamp fields are excluded from the canonical form by construction. Equivalently: the entry-on-the-wire equals the canonical-form bytes plus the chain-stamp fields appended; the MAC covers only the canonical-form bytes."

### Q-16. Witness verifier — what exactly does "structurally consistent" mean?

Spec §7 says a verifier without a master key under `--strict` produces FAIL; without `--strict`, it produces `"structurally consistent, key-bound verification skipped"`. The spec doesn't formally define which steps a witness verifier executes. A reasonable interpretation is "steps 1–7" (format, header, structure) plus skip step 8 (`key_fingerprint`) and step 9 (MAC), then optionally execute step 10 (Merkle) and steps 11–12 (signature, cadence). But "structurally consistent" with no further detail invites variance: implementer A skips 8–9; implementer B skips 8–12. **Ask:** add a normative table to §7 or §10: "Witness verifier (no `--master-key`) executes steps 1, 2, 3, 4, 5, 6, 7, 10, 11, 12. Skips steps 8 and 9 (which require IKM access). The output is `Status: PASS-STRUCTURALLY, key-bound verification skipped`. Institutional self-verification MUST use `--master-key` and execute all 12 steps." This resolves the witness-mode ambiguity Aanya saw and addresses the "different implementations skip different steps" risk.

### Q-17. Concurrent seal signing — event ingestion during HSM signature computation?

Spec §4.2.2 addresses late-binding: events arriving after the seal-date UTC boundary are included in the next day's seal. But the spec doesn't address the smaller window between "we have collected all events for day D" and "the HSM has finished signing the root for day D." If a new event arrives during HSM signing, does the ledger queue it (and re-roll the seal), or treat it as late-binding? The 60-min SLA in §4.3 implies a clear cutover, but the cutover semantics aren't normated. **Ask:** add to §4.2 or §10: "The daily seal MUST be computed from all events whose `captured_at` timestamp falls within that UTC day. Once the institution begins computing the seal's Merkle root for a tenant-day, the ledger MUST NOT include any further events in that day's seal; events arriving after the cutover are late-binding and roll into the next day's seal per §4.2.2. The cutover discipline is institution-defined within the §4.3 60-minute SLA window." This pins the operational contract that the byte-level signature computation depends on.

### Q-18. Key-rotation mid-seal — `key_versions` semantics named in §4.2?

Spec §10.10 (Rotation crossing the seal boundary) addresses rotation across two seal dates. Test vector 010 (`tenant-ikm-rotation-mid-day`) exercises rotation within a single seal date and the seal record's `key_versions` is `[1, 2]`. Spec §4.2 says the `key_versions` list contains "the `key_version` values present in the day's chain entries" — which covers the within-day case implicitly. But the spec text doesn't explicitly state the within-day case as a first-class scenario; a maintainer reading §4.2 alone might assume `key_versions` is always single-element. **Ask:** add to spec §4.2 a sentence: "When key rotation occurs within a single tenant-day, the seal record's `key_versions` list contains all key-version values present in the day's events, in ascending numeric order (e.g., `[1, 2]` for a rotation from v1 to v2 mid-day). Test vector 010 demonstrates the bytes." This makes within-day rotation a normative scenario in the spec text, not just a test-vector artifact.

### Q-19. Algorithm binding in dual-algorithm `sign_payload` — one payload, two signatures, or two payloads?

Spec §4.3 shows that `sign_payload` includes the `algorithm` string on the second line, closing algorithm-confusion attacks. Test vector 015 (the dual-algorithm case) is described in the README. But the spec doesn't explicitly clarify: under dual-algorithm posture, do both signatures cover *the same* `sign_payload` bytes (with one `algorithm` value, presumably the primary), or are there *two separate* `sign_payload` byte sequences (each with its own `algorithm` field)? Either design is defensible; the byte-level contract is different. **Ask:** clarify in §4.3 dual-algorithm subsection: "Under dual-algorithm posture (§4.3.2), each algorithm in the `signatures[]` list is computed over its own algorithm-specific `sign_payload`. The `algorithm` field in each `sign_payload` reflects that algorithm's name. This means a Dilithium signature is over `sign_payload_dilithium` (with `algorithm = "dilithium3"` on line 2), not over `sign_payload_ed25519`. This closes algorithm-confusion attacks across the two algorithms; a single shared payload would let an attacker substitute one algorithm's signature with the other's without bytes-level detection." Or, if the design is the opposite (one payload, two signatures), state that with the security justification.

### Q-20. Verifier step ordering — strict order, or only data-dependency order?

Spec §7 says "A conforming verifier MUST execute the following ordered procedure." Negative N006 explicitly tests step 8 (fingerprint) before step 9 (MAC), proving order is load-bearing. But the spec doesn't clarify whether the order is "strict everywhere" or "only where data dependencies require it." For example, step 12 (cadence check) doesn't depend on steps 8–11; an implementation that performs cadence early as a quick rejection is arguably more efficient. The reference implementation's choice constrains the conformance contract; the spec text should pin it. **Ask:** clarify in §7: "The step order is normative for steps with data dependencies. Specifically: step 8 (`key_fingerprint` lookup) MUST precede step 9 (MAC compute), because step 9's expected MAC depends on the IKM resolved by step 8 — reordering them allows N006-class attacks to be misreported as MAC failures. Steps 1–7 are sequential because they establish preconditions for steps 8+. Steps 10–12 may be executed in any order relative to each other, provided each step's failure reason is reported with the correct step number. An implementation that skips a step entirely is non-conformant."

### Q-21. ISO8601 date format in `sign_payload` — date-only required?

Spec §4.3 shows `iso8601_date(tenant_day)` in the `sign_payload`. Test vectors show this as `2026-05-06` (date-only). ISO8601 is a family; the spec should clarify that the date-only form is required and forms with time/timezone (`2026-05-06T00:00:00Z`) are non-conformant. The signature bytes change with the format. **Ask:** add to §4.3: "The `iso8601_date(tenant_day)` is the date in `YYYY-MM-DD` form (no time component, no timezone, no fractional seconds). The verifier MUST reject seal records where this field is in any other ISO8601 form. The reference Go implementation uses Go's `time.Time.Format("2006-01-02")` to produce the canonical form; clean-room implementations MUST produce byte-identical output for any given UTC date."

### Q-22. Merkle-root hex — case + zero-padding pinned?

The test vector `sign_payload_single_hex` decodes to a `hex(merkle_root)` of 64 lowercase hex characters (corresponding to the 32-byte hash). The spec doesn't state whether a root with a leading zero byte should serialize as `01...ff` (64 chars) or omit leading zeros. The vectors resolve it (always 64 chars, lowercase). **Ask:** add to §4.3: "The `hex(merkle_root)` and `hex(hkdf_inputs_digest)` values MUST be the 64-character lowercase hexadecimal representation of the corresponding 32-byte hash, zero-padded to exactly 64 characters. Implementations that strip leading zeros or use uppercase hex are non-conformant — the bytes go into the Ed25519 signature, so any difference produces a non-matching signature."

### Q-23. Verifier exit-code contract — defined for CLI verifiers?

Spec §7 describes failure modes and reason strings. It doesn't define CLI exit codes. The reference verifier (`E:\dev\ffiec\verifier\`) presumably has an exit-code convention; the spec text doesn't formalize it. Examiners writing scripts to batch-verify chains over an examination period need to know which exit codes mean PASS vs FAIL vs invalid input. Two independent verifiers might disagree. **Ask:** add a short appendix to §7 (or to `docs/operator-guide.md`): "Verifier CLI exit codes — 0 for `PASS` / `PASS-STRUCTURALLY` (witness mode); 1 for `FAIL` (chain integrity violation per any step's failure mode); 2 for structural / input error (unparseable file, missing required headers); 3 for configuration error (missing `--master-key` under `--strict`, unknown algorithm, file format unsupported by verifier version). Implementations MAY define additional codes ≥4 for vendor-specific diagnostics; the conformance contract is codes 0–3."

### Q-24. Constant-time comparison — MUST or RECOMMENDED?

Spec §4.1 property 4 and §10.8 use mixed language: the property says "MUST use a constant-time equality primitive" but the §10.8 section heading is "Constant-time comparison" with text that uses "RECOMMENDED" for stdlib helpers (`subtle.ConstantTimeCompare` in Go). A clean-room reading produces ambiguity: is the constant-time discipline a cryptographic requirement (MUST) or a performance optimization (RECOMMENDED)? **Ask:** clarify in §10.8: "Implementations MUST use constant-time equality for the `key_fingerprint` check (§7 step 8) and the `payload_hash` MAC check (§7 step 9). The reference Go implementation uses `subtle.ConstantTimeCompare`. A custom constant-time compare is acceptable if the implementation has verified it is constant-time against the platform's timing side-channels. A plain byte-equality (`==` for Go byte slices via `bytes.Equal`) is non-conformant; `bytes.Equal` is *not* constant-time and leaks early-mismatch position via timing." This separates the mandatory property (constant-time) from the recommended approach (use stdlib).

### Q-25. HKDF length encoding — integer parameter vs byte serialization in `hkdf_inputs_digest`?

The test-vector README clarifies that `length_LE32 = (32).to_bytes(4, "little") = 0x20 0x00 0x00 0x00`, and that `hkdf_inputs_digest = SHA-256(HKDF_SALT || info_for_tenant || length_LE32)`. Spec §4.1 uses the integer 32 as the HKDF `length` parameter, but the seal record's `hkdf_inputs_digest` requires the 4-byte little-endian encoding. A maintainer might confuse the two: HKDF `length=32` (an integer, passed to the HKDF function) vs `length_LE32` (the 4-byte little-endian serialization, fed into the SHA-256 hash). The two are related but distinct. **Ask:** add to §4.2 (seal record subsection): "The `hkdf_inputs_digest` includes `length_LE32`, the 4-byte little-endian representation of the integer 32 (the HKDF output length parameter). The bytes are: `0x20 0x00 0x00 0x00`. This differs from the HKDF `length` parameter itself, which is the integer 32 passed to HKDF-SHA-256. A naive implementation that hashes the ASCII string `"32"` produces a different digest and is non-conformant." Test-vector hex confirms this; spec text should match.

### Q-26. Verifier output — both step number and reason required?

Negative test vectors specify both step (e.g., `step 8`) and reason (e.g., `"key_fingerprint mismatch at seq 1"`). The spec §7 says the verifier "reports the most specific reason and stops processing." It doesn't formalize whether the step number is part of the output. A verifier that emits only the reason string passes the description-level check but may fail a byte-exact harness check. **Ask:** clarify in test-vector README or spec §7: "Verifier output for a failed run MUST include both the failing step number and the reason string in a normative format. The reference output format is: `Status: FAIL\nStep: N\nReason: <text>` (three lines, exact field labels, exact line breaks). The reference Go implementation produces this format; conforming implementations MUST match byte-for-byte." This makes the output a first-class part of the conformance contract, not just a description.

### Q-27. Empty audit file — header alone, or no file at all?

Spec §4.4 and §6 (Wire format / Storage) define the line-oriented file format with a header on line 1 and entries thereafter. But for a tenant-day with zero events, what does the file contain? Just the header line? An empty file? No file? The verifier behavior depends on the answer. **Ask:** add to §4.4 or §6: "An audit file's first line MUST be the header. A tenant-day file with zero events contains exactly one line — the header — terminated with a single `\n` byte. The verifier accepts this as a valid file and computes the empty-tree Merkle root per §4.2 (`SHA-256(b'')`). A file with zero bytes is structurally invalid and rejected at step 2 (file-format validation) with reason `"empty file: header missing"`."

### Q-28. Header HKDF-digest mismatch — strict-only behavior, or default?

Spec §7 step 2 says a mismatched `hkdf_inputs_digest` causes the verifier to "reject the file." Negative N010 confirms the rejection. But the spec doesn't disambiguate strict vs non-strict mode for this specific check. Step 8 + 9 have a documented strict/non-strict split (FAIL vs `"key-bound verification skipped"`); does step 2 also have one? Reading the spec literally, step 2 is unconditional rejection — there's no witness-mode equivalent for header validation. That seems correct (a malformed header isn't a missing-IKM case), but it should be stated. **Ask:** clarify in §7 step 2: "The header `hkdf_inputs_digest` validation is unconditional — it runs in both strict and non-strict modes, and a mismatch is always a FAIL with reason `'header HKDF inputs do not match running v1 inputs'`. There is no witness-mode equivalent for header validation; a mismatched header signals a non-FFIEC-posture file (or a misconfigured verifier), neither of which is recoverable by relaxing the check." This closes the strict/non-strict ambiguity for the pre-flight stage.

## Stopping criterion verdict

**0 Partials, 28 supporting questions Q-1 through Q-28.**

Aanya's persona files no headline-grade Partial because, in her judgment, the spec's normative posture is sound and the reference test vectors close every byte-level gap she encountered. **Question groupings.**

- **Canonical form & numerics (Q-8 through Q-12):** RFC 8785 binding, IEEE-754 double range, pre-flight validation, empty-day root, streaming-vs-in-memory Merkle. Five questions about the JSON-canonical-form contract.

**Disposition expectation.** Most of these are short text additions to the spec — a paragraph each, often a single sentence. A few (Q-2, Q-13, Q-19) call for new test vectors; those are larger but each is bounded (a single fixture extension). None require redesign; all are clarification.
