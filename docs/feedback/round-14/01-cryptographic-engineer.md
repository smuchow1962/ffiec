## Headline

The cryptographic floor of this v1.0 bundle is sound and — for the dual-algorithm transitional design specifically — is the most carefully-specified post-quantum coexistence text I have read in any banking-adjacent chain-of-custody artifact. Variant B is normative (each algorithm covers its own algorithm-bound `sign_payload`), the verifier pseudocode in design 07 §4.3 reconstructs the algorithm-specific payload before each verify call (the second line of the payload is `entry.algorithm`, not `seal.algorithm`), and the spec §7 step 11 enumeration of cases (a) through (e) closes the algorithm-confusion attack class by construction rather than by composition. Negative case N019 ("one valid + one invalid") is the load-bearing test — a Variant A implementation would mistakenly let an Ed25519 signature satisfy a Dilithium-named slot, and the description.md for N019 names this attack and the construction-level defence against it. That is the right disposition.

The HKDF-`info` binding has the correct shape: `info_for_tenant = HKDF_INFO_BASE || b"|" || utf8(tenant_id)` with the `tenant_id` regex constrained to exclude the `|` byte (0x7C). Boundary-confusion across two distinct tenant_ids is structurally impossible because the only byte that could end the constant prefix cannot appear inside the tenant identifier. The fixed-32-byte `prev_hash` rule in §4.1 inviolate property #2 closes the length-prefix attack on the MAC input `prev_hash || canonical`. The `key_fingerprint = SHA-256(utf8(tenant_id) || ikm)[:16]` check at §7 step 8 — performed before any MAC compute — catches botched rotation precisely (the `key_version` looked up the wrong IKM; the MAC would have failed downstream but the report would have read "MAC mismatch" rather than "looked-up IKM does not match recorded fingerprint"). The 16-byte truncation is defensible against the public-stamp offline grind concern given the §10.6 32-byte IKM minimum.

The byte-level conformance fixture in `chain_vectors.json` reproduces from the published constants by independent recomputation. I confirmed `session_key_v1_hex`, `session_key_v2_hex`, `key_fingerprint_v1_hex`, `key_fingerprint_v2_hex`, and `hkdf_inputs_digest_hex` against the recipe in §3 of the spec; the values agree. The two `sign_payload_*_text` blocks reproduce byte-for-byte from `algorithm="ed25519"`, `format_version="v1"`, `tenant_id="tenant-ffiec-test-1"`, the recorded seal_date, the published Merkle roots, and the published `hkdf_inputs_digest`. The corresponding `sign_payload_*_hex` blocks are the lowercase-hex encoding of the text-form bytes — also confirmed.

I cannot pass the bundle at 0/0 this round. Three issues block; each is mechanical. The bundle is otherwise the strongest cryptographic artifact set I have read for a regulator-adjacent AI chain-of-custody.

**Verdict.** 1 gap, 2 partials.

## Questions raised by this read (3-5, scoped to my seat)

**Q-1.** Spec §4.2 introduces `signatures` as an optional list and §4.3 sign_payload composition is the same recipe whether the seal is single-algorithm or dual-algorithm. The spec's worked-example clarification SHOULD say explicitly: when `signatures` is present, the top-level `signature` and `algorithm` fields hold the PRIMARY entry's bytes, AND that primary entry is ALSO included as the first element of the `signatures` list (not omitted as a duplicate). Spec §4.2 row text reads: "the `signatures` list contains the full co-signing set INCLUDING the primary entry." That is correct as English; the failure mode I want closed is an implementer who reads "the primary algorithm's signature for backward compatibility" and OMITS the primary entry from `signatures` to avoid duplication. The §4.2 row already names this; consider adding one line to the Variant B clarification ("the `signatures` list MUST include the primary algorithm's entry") so a literal reader cannot reach the wrong conclusion.

**Q-2.** The `hkdf_inputs_digest = SHA-256(HKDF_SALT || info_for_tenant || length_LE32)` includes a 4-byte little-endian encoding of the HKDF output length. The output length is fixed at 32 for v1; the digest binds it. If a future spec version (v1.1+) changes the HKDF output length — say to 64 bytes for an HMAC-SHA-512 chain — the `length_LE32` field gives clean format-drift detection at §7 step 2, which is correct. **My question is on byte ordering**: the field name `length_LE32` is read as "length as 32-bit little-endian," and `(32).to_bytes(4, "little")` in the README confirms little-endian. The inputs to `SHA-256` are little-endian within the length field; everything else (salt, info) is byte-string concatenation with no endianness. This is unambiguous in the published fixture (the digest reproduces). The naming convention `LE32` could be misread as "32 bytes in little-endian" rather than "32-bit (4 byte) little-endian." Suggest the spec §3 definition row spell out explicitly: "`length_LE32 = 32 encoded as 4-byte little-endian, i.e. b'\\x20\\x00\\x00\\x00'`." This is purely a clarity question; the fixture pins the right bytes.

**Q-3.** The N020 algorithm/key-type-mismatch case description.md says the verifier MUST detect the mismatch at public-key resolution time, BEFORE the underlying cryptographic Verify call. The reason given is "Implementations that pass the public key to the verify call without checking algorithm-type compatibility will produce the generic failure message; that is non-conforming." This is correct as a behavioural specification, but several language stdlib Verify primitives (Go's `ed25519.Verify`, Python's `cryptography` library's `Ed25519PublicKey.verify`) accept a typed key as input and refuse at the type system level when the wrong algorithm's key is passed. A conforming implementation that types its public-key registry correctly cannot reach the cryptographic Verify call with a wrong-type key — the type system catches it. The spec text "BEFORE the underlying cryptographic Verify call" is correct intent but reads as a runtime ordering requirement. Suggest design 07 §4.3 adds a sentence: "Conforming implementations whose public-key registry is typed (the registry resolves to `Ed25519PublicKey`, `MLDSAPublicKey`, etc., per the algorithm) check the type at resolution time and the language's type system enforces the algorithm/key-type binding. The reason-string contract is independent of the implementation mechanism — the verifier reports the specific reason whether the check is at runtime or at the type system."

**Q-4.** The `key_fingerprint = SHA-256(utf8(tenant_id) || ikm)[:16]` truncation to 16 bytes is acceptable given the §10.6 32-byte IKM minimum, but the choice of `[:16]` versus `[16:]` versus other 16-byte windows over the 32-byte SHA-256 output is unstated. The fixture pins `[:16]` (first 16 bytes) — the published `key_fingerprint_v1_hex = 54c245a894b81d788d372badc563531f` is the leading 16 bytes of `SHA-256(utf8("tenant-ffiec-test-1") || ikm_v1)`. An implementer reading spec §3 ("`SHA-256(utf8(tenant_id) || ikm)[:16]`") gets the right answer because Python `bytes[:16]` is unambiguous, but Go `slice[:16]` is also unambiguous in the same direction. I confirm the pinned fixture matches `[:16]` rather than `[16:]`. The spec text is clear; this is a documentation-style question only.

```go
type StreamingMerkle struct {
    levels [][]byte
}

func (s *StreamingMerkle) Add(leafHash []byte) {
    // ... only invoked when there is a leaf to add ...
}

func (s *StreamingMerkle) Root() []byte {
    var current []byte
    for _, h := range s.levels {
        if h == nil { continue }
        if current == nil {
            current = h
        } else {
            x := sha256.Sum256(append(append([]byte{0x01}, h...), current...))
            current = x[:]
        }
    }
    return current
}
```
