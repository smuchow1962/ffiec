## Headline

The cryptographic floor of this v1.0 bundle is sound and — for the dual-algorithm transitional design specifically — is the most carefully-specified post-quantum coexistence text I have read in any banking-adjacent chain-of-custody artifact. Variant B is normative (each algorithm covers its own algorithm-bound `sign_payload`, per spec §4.2 and design 07 §4.3), the verifier pseudocode in design 07 §4.3 reconstructs the algorithm-specific payload before each `verify_for_algorithm` call (line 2 of the reconstructed payload is `entry.algorithm`, not `seal.algorithm`), and the spec §7 step 11 enumeration of cases (a)–(e) closes the algorithm-confusion attack class by construction rather than by composition. Negative case N019 ("one valid + one invalid") is the load-bearing test — a Variant A implementation would mistakenly let an Ed25519 signature satisfy a Dilithium-named slot, and the description.md for N019 names this attack and the construction-level defence against it. That is the right disposition.

The HKDF-`info` binding has the correct shape: `info_for_tenant = HKDF_INFO_BASE || b"|" || utf8(tenant_id)`, with the `tenant_id` regex constrained to alphanumerics plus underscore, dot, and hyphen — so the `|` byte (0x7C) cannot appear inside the tenant identifier. Two distinct tenant_ids structurally produce different `info` byte sequences; the boundary-confusion attack class is closed by the character set, not by length encoding. The fixed-32-byte `prev_hash` rule in §4.1 inviolate property #2 closes the length-prefix attack on the MAC input `prev_hash || canonical`. The `key_fingerprint = SHA-256(utf8(tenant_id) || ikm)[:16]` check at §7 step 8 — performed before any MAC compute — catches botched rotation precisely (the recorded `key_version` looked up the wrong IKM; the MAC would have failed downstream but the report would have read "MAC mismatch" rather than "looked-up IKM does not match recorded fingerprint"). The 16-byte truncation is defensible against the public-stamp offline-grind concern given the §10.6 32-byte IKM minimum.

The byte-level conformance fixture in `chain_vectors.json` reproduces from the published constants by independent recomputation. I confirmed each of the following by recomputing from the spec recipe in §3 and §4.1, with the published HKDF constants and `tenant-ffiec-test-1` as the tenant identifier:

- `session_key_v1_hex` — agrees byte-for-byte.
- `session_key_v2_hex` — agrees byte-for-byte.
- `key_fingerprint_v1_hex` and `key_fingerprint_v2_hex` — agree byte-for-byte against `SHA-256(utf8(tenant_id) || ikm)[:16]` for each generation.
- `hkdf_inputs_digest_hex = 6f8a5005cabb2eab8b347254d0c94c2d585a7e5a5a82398c5aeaea074c727d65` — agrees against `SHA-256(salt || info_for_tenant || length_LE32)` where `length_LE32 = (32).to_bytes(4, "little")`.
- Per-event `payload_hash` for `single_chain[0..4]` and `rotation_chain[0..4]` — every value agrees, including the rotation-boundary entry (seq=4) where `prev_hash` carries the bytes from the old IKM's chain (entry seq=3 under v1) but the MAC is computed under `session_key_v2`. The chain link is unbroken because `prev_hash` is the previous payload_hash bytes regardless of which IKM produced them; the MAC compute uses the correct session key per the per-entry `(tenant_id, key_version) → IKM` lookup.
- `merkle_root_single_hex` and `merkle_root_rotation_hex` — agree against an independent RFC 6962 streaming construction over the ordered `payload_hash` list.
- `sign_payload_single_text` and `sign_payload_rotation_text` — reproduce as the §4.3 composition `"ffiec.chain-of-custody.v1\n" || "ed25519\n" || "v1\n" || tenant_id || "\n" || seal_date || "\n" || hex(merkle_root) || "\n" || hex(hkdf_inputs_digest)` (note the closing `hex(hkdf_inputs_digest)` line carries no trailing newline, which the published text confirms).
- `sign_payload_single_hex` and `sign_payload_rotation_hex` — agree as the lowercase-hex encoding of the corresponding text bytes.
- `empty_day_merkle_root = e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855` — agrees against `SHA-256("")` (the empty-input SHA-256 digest per FIPS 180-4).

The fixture is internally consistent. Two independent v1.0 implementations consuming the published constants and inputs produce byte-identical chain artifacts.

The three new fixture-side improvements in this bundle — the `signatures` MUST-include-primary clarification at §4.2, the literal `gen_ai.` namespace discriminator at §7 step 12a with the inline-timing requirement, and the algorithm string table plus `length_LE32` clarification in `spec/test-vectors/README.md` — close the byte-form drift, the per-event-check timing ambiguity, and the namespace-discriminator gap that a literal-reading implementer could otherwise have resolved differently.

I find no remaining cryptographic gaps. The dual-algorithm fixture deferral (cases 015 and N017–N019) is appropriately scoped — the byte-level fixture for the post-quantum half cannot be locked until the v1.x ship that selects the FIPS 204 / 205 parameter set, and the algorithm string table now pins the byte-form for those identifiers in advance so the fixture can be added without any further normative decision. The N020 case is computable today under v1.0 single-algorithm posture; the description.md is precise on what the verifier must report and at which step. The streaming-Merkle empty-input contract at design 03 §3.1 explicitly names the wrap-with-empty-check pattern that closes the implementation drift in generic Merkle libraries.

**Verdict.** 0 gaps, 0 partials. **PASS.**

## Questions raised by this read (3–5, scoped to my seat)

**Q-1.** Spec §4.2 commits Variant B normative for the `signatures` list and specifies that the list MUST include the primary algorithm's entry, with the top-level `signature`/`algorithm` fields and the corresponding list entry carrying byte-identical bytes. A literal reader may still be tempted to optimise storage by encoding the list with the primary entry omitted ("the top-level fields already cover it"). The spec text closes this in English ("a verifier processing only the list is complete"). Consider adding one positive test vector to the v1.x dual-algorithm fixture once it ships: a parallel encoding of the same seal with the primary entry both INCLUDED in the list and OMITTED from the list, with the spec disposition that the omitted-form is non-conformant and a verifier MUST refuse it. The byte-level discriminator would be the `signatures` list cardinality (2 vs 1 under dual-algorithm posture); the test would catch the storage-optimisation drift before it lands in production.

**Q-2.** The `key_fingerprint = SHA-256(utf8(tenant_id) || ikm)[:16]` truncation to 16 bytes is acceptable given the §10.6 32-byte IKM minimum, but the spec §3 definition row could be one line more explicit on the truncation direction. The fixture pins `[:16]` (leading 16 bytes): `key_fingerprint_v1_hex = 54c245a894b81d788d372badc563531f` is the leading 16 bytes of `SHA-256(utf8("tenant-ffiec-test-1") || ikm_v1)`. The Python notation `bytes[:16]` and the Go slice `slice[:16]` are unambiguous in the same direction, so a careful implementer reaches the right answer. A one-line clarification in spec §3 — "the first 16 bytes of the 32-byte SHA-256 output, i.e. bytes 0..15 inclusive" — closes any residual ambiguity for an implementer working from the spec text alone, without checking the fixture. Documentation polish only; the conformance property is locked at the byte level by the published fixture.

**Q-3.** The N020 case description.md says "The verifier MUST detect the algorithm/key-type mismatch at public-key resolution time (BEFORE the underlying cryptographic Verify call)." Several language stdlib Verify primitives (Go's `ed25519.Verify`, Python's `cryptography` library's `Ed25519PublicKey.verify`, .NET's `Ed25519` public-key types) accept a typed key as input and refuse at the type system level when the wrong algorithm's key is passed — a conforming implementation that types its public-key registry correctly cannot reach the cryptographic Verify call with a wrong-type key because the type system catches it. The spec text "BEFORE the underlying cryptographic Verify call" is correct intent but reads as a runtime ordering requirement. Consider one sentence in design 07 §4.3 confirming that the reason-string contract is independent of the implementation mechanism: a typed-registry implementation reaches the specific reason at type-resolution time; a runtime-typed implementation reaches it at the explicit algorithm-compatibility check. Both are conforming. The reason-string is the contract, not the code path.

**Q-4.** The algorithm string table at `spec/test-vectors/README.md` lines 19–28 carries an asymmetric naming convention: seal-record signature algorithms use lowercase + underscores (`ed25519`, `dilithium3`, `slh_dsa_shake_128s`), while the per-entry chain-stamp `ffiec.chain.algorithm` name uses uppercase + dashes (`HMAC-SHA-256`). The README explicitly notes the legacy-compatibility reason. The asymmetry is locked at the byte level (each form is bound into its respective payload — `sign_payload` line 2 for the seal, the chain-stamp attribute for the per-entry forensic field) and a conforming implementation cannot drift. My only observation: the FIPS 204 / 205 standards use the parameter-set names `ML-DSA-44`, `ML-DSA-65`, `ML-DSA-87`, `SLH-DSA-SHAKE-128s`, etc. — the spec's `dilithium3` is the original Dilithium round-3 parameter-set name; FIPS 204 renames the same parameter set to `ML-DSA-65`. When the v1.x ship lands, the algorithm-string table will need a normative call on whether `dilithium3` (round-3 NIST submission name, what the v1.0 README pins today) or `ml_dsa_65` (FIPS 204 standardised name) is the byte-form. This is a question for the v1.x working group, not a v1.0 finding. The v1.0 byte-form is locked; the v1.x working group selects the FIPS-aligned identifier when the post-quantum half ships.

**Q-5.** The 30-day spec-patch SLA at §4.3.2 covers credible attacks on Ed25519, HMAC-SHA-256, or SHA-256. The narrative names 180 days for signature breaks and 90 days for HMAC/SHA-256 breaks. The shorter window for HMAC/SHA-256 is appropriate (a HMAC-SHA-256 / SHA-256 break invalidates every chain entry ever produced under v1; a signature break invalidates only the seal layer, with the per-event MAC still bearing integrity assurance under the un-broken HMAC-SHA-256 assumption). One operational consideration the cryptographic seat would name: a credible SHA-256 collision attack — even if not a preimage attack — affects the RFC 6962 Merkle construction (the leaf-prefix and node-prefix domain separation does not protect against an attacker who can construct two distinct leaf inputs that hash to the same leaf_hash). The 90-day migration window for SHA-256 breaks correctly captures this; the per-event HMAC-SHA-256 is comparatively more robust because the keyed nature defeats collision attacks (an attacker would need a key-recovery break, not a collision break). I read this correctly into §4.3.2's tighter window. No finding; observation only.
